Le DELETE qui a vidé une table de production

C'était un vendredi après-midi. Un développeur d'une équipe que je connais exécutait un script de nettoyage pour supprimer les comptes de test de la base de données de production. La requête était censée être :

DELETE FROM users WHERE email LIKE '%@test.example.com';

Ce qui a réellement été exécuté :

DELETE FROM users;

La clause WHERE avait été accidentellement supprimée lors de l'édition du script. La requête s'est exécutée en 0,8 seconde. Les 340 000 utilisateurs ont disparu. L'application était instantanément hors service. La restauration a pris trois heures à partir d'une sauvegarde vieille de six heures, ce qui signifie que six heures d'inscriptions en production ont été définitivement perdues.

C'est l'anti-pattern SQL le plus spectaculaire, mais il est loin d'être le seul dangereux. Certains anti-patterns détruisent les données. D'autres détruisent silencieusement les performances — vous ne le remarquez que lorsque votre base de données traite 10 millions de lignes au lieu de 10 000 et que chaque appel API prend 8 secondes au lieu de 80 millisecondes. Quelques-uns sont des bugs de logique subtils qui produisent des résultats faux tout en paraissant parfaitement corrects — le motif NOT IN avec NULL étant le pire de tous.

Ce guide couvre les 10 motifs qui causent le plus de dégâts dans les systèmes de production réels, avec des exemples reproductibles et les corrections exactes.

Anti-pattern 1 : NOT IN avec une sous-requête — le résultat faux silencieux

1NOT IN avec NULL dans la sous-requête
Critique — résultats faux

C'est le bug SQL le plus dangereux car il ne produit aucune erreur. Votre requête s'exécute, renvoie des résultats, et tout semble normal — sauf que vous perdez des lignes qui devraient être présentes, ou vous n'obtenez aucune ligne alors que vous en attendez beaucoup.

La cause est la logique à trois valeurs de SQL. SQL n'a pas seulement VRAI et FAUX — il a VRAI, FAUX et INCONNU. Toute comparaison avec NULL s'évalue à INCONNU. Et voici le point critique : NOT IN filtre les lignes où la comparaison n'est pas VRAIE. INCONNU n'est pas VRAI. Donc toute ligne comparée à une valeur NULL dans la sous-requête est filtrée.

Le bug reproductible
-- Préparation : table users avec une ligne où country est NULL
CREATE TABLE users (id INT, name VARCHAR(50), country VARCHAR(2));
INSERT INTO users VALUES
  (1, 'Alice', 'FR'),
  (2, 'Bob',   'DE'),
  (3, 'Carol', NULL);   -- ← Ce NULL est la bombe

-- Pays bloqués
CREATE TABLE blocked_countries (country_code VARCHAR(2));
INSERT INTO blocked_countries VALUES ('US'), ('CN');

-- Attendu : lignes 1, 2, 3 (aucune n'est US ou CN)
-- Obtenu :   0 lignes (!)
SELECT id, name FROM users
WHERE country NOT IN (SELECT country_code FROM blocked_countries);

-- Pourquoi ? Le NOT IN se développe en :
-- WHERE country != 'US' AND country != 'CN'
-- Pour la ligne 3 : NULL != 'US' → INCONNU ; INCONNU AND ... → INCONNU
-- INCONNU n'est pas VRAI → la ligne 3 est filtrée
-- Mais comme la ligne 3 est filtrée, la requête filtre aussi les lignes 1 et 2
-- selon la façon dont l'optimiseur gère NULL dans la liste NOT IN.
-- Le comportement exact dépend de la base de données, mais la règle la plus sûre est :
-- n'utilisez jamais NOT IN si la sous-requête peut renvoyer NULL.
Correction 1 — NOT EXISTS (recommandé)
-- NOT EXISTS gère correctement NULL
-- Renvoie les lignes 1, 2, 3 comme attendu
SELECT id, name FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM blocked_countries b
  WHERE b.country_code = u.country
);
-- NOT EXISTS court-circuite correctement :
-- Pour la ligne 3 (country = NULL) : la sous-requête WHERE NULL = country_code
-- ne correspond jamais, donc NOT EXISTS est VRAI. La ligne 3 est incluse. ✓
Correction 2 — Motif anti-jointure LEFT JOIN
-- Gère également NULL correctement, et souvent plus performant sur de grandes tables
SELECT u.id, u.name
FROM users u
LEFT JOIN blocked_countries b ON u.country = b.country_code
WHERE b.country_code IS NULL;
-- Les lignes sans correspondance (y compris country NULL) sont renvoyées ✓
Correction 3 — Ajouter WHERE IS NOT NULL (si les NULL doivent être exclus)
-- Si vous voulez exclure explicitement les pays NULL
SELECT id, name FROM users
WHERE country IS NOT NULL
  AND country NOT IN (SELECT country_code FROM blocked_countries
                      WHERE country_code IS NOT NULL);

Anti-pattern 2 : SELECT * — trois coûts qui s'accumulent

2SELECT * — l'habitude apparemment inoffensive
Moyenne — performance + fragilité

La plupart des développeurs savent que SELECT * est « mauvais ». Moins savent exactement pourquoi, ce qui signifie qu'ils ne savent pas quand cela importe vraiment par rapport à quand c'est acceptable. Il y a trois coûts distincts, et chacun s'aggrave avec l'échelle.

Coût 1 — Pas d'index-only scans

PostgreSQL (et d'autres bases) peut répondre à une requête entièrement depuis un index sans toucher aux lignes réelles de la table — un « index-only scan ». C'est beaucoup plus rapide car les index sont plus petits et plus susceptibles d'être en cache. SELECT * détruit cela : comme l'index ne contient pas toutes les colonnes, la base doit lire le tas (les données de la table) pour chaque ligne correspondante.

-- Table avec un index sur (user_id)
CREATE TABLE events (
  id         UUID PRIMARY KEY,
  user_id    BIGINT,
  event_type VARCHAR(50),
  payload    JSONB,    -- Potentiellement volumineux
  created_at TIMESTAMPTZ
);
CREATE INDEX ON events(user_id);

-- ❌ Force une lecture du tas pour chaque ligne — l'index seul ne suffit pas
SELECT * FROM events WHERE user_id = 42;

-- ✅ Index-only scan possible si l'index couvre les colonnes nécessaires
SELECT id, event_type, created_at FROM events WHERE user_id = 42;

-- Encore mieux : créer un index couvrant
CREATE INDEX ON events(user_id) INCLUDE (id, event_type, created_at);
-- Maintenant la requête ci-dessus ne touche jamais le tas

Coût 2 — Fragilité du schéma

Votre frontend s'attend à ce que users ait 8 colonnes. Vous ajoutez une colonne password_reset_token pour une nouvelle fonctionnalité. Chaque endpoint API qui fait SELECT * FROM users expose maintenant ce token dans sa réponse. Ce n'est pas hypothétique — j'ai vu ce motif causer des incidents de sécurité en production. La « sécurité par accident » que SELECT * fournit est la pire : vous ne savez pas ce que vous exposez.

Coût 3 — Bande passante inutile

Si votre table products a une colonne description TEXT d'une moyenne de 2 Ko, et qu'une requête de liste qui renvoie 200 produits fait SELECT *, vous transférez 400 Ko de texte de description que la page de liste n'affiche jamais. À 100 requêtes par seconde, cela représente 40 Mo/s de trafic réseau inutile entre la base de données et l'application. Utilisez SELECT id, nom, prix, miniature_url pour la liste, et ne récupérez le produit complet (description incluse) que lorsqu'un utilisateur consulte la page de détail.

-- ❌ Requête de liste — toutes les colonnes, y compris les volumineuses
SELECT * FROM products WHERE category_id = 5 ORDER BY created_at DESC LIMIT 20;

-- ✅ Requête de liste — uniquement ce que l'UI affiche
SELECT id, name, price, stock, thumbnail_url, slug
FROM products
WHERE category_id = 5
ORDER BY created_at DESC
LIMIT 20;

-- ✅ Requête de détail — produit complet quand l'utilisateur clique
SELECT * FROM products WHERE slug = 'widget-pro-xl';
-- (SELECT * est acceptable ici — nous avons besoin de tout)
Quand SELECT * est acceptable : Dans une vue de détail qui a réellement besoin de toutes les colonnes, dans des scripts d'administration rapides ponctuels, ou pour interroger une petite table de référence avec un schéma stable. Le mot-clé est « intentionnellement » — vous savez exactement ce que vous sélectionnez, vous ne laissez pas le hasard décider.

Anti-pattern 3 : Fonctions sur colonnes indexées dans le WHERE

3Fonction sur colonne indexée — le parcours complet invisible
Élevée — performance

C'est probablement l'anti-pattern de performance le plus courant que je rencontre lors des revues de code. La requête a l'air propre, la logique est correcte, mais la base de données ignore l'index et lit chaque ligne de la table.

La raison est simple : un index sur created_at stocke les valeurs brutes des timestamps en ordre trié. Si vous appliquez YEAR(created_at) ou DATE(created_at) à la colonne, la base de données devrait évaluer la fonction pour chaque valeur stockée afin d'appliquer le filtre — ce qui annule l'intérêt de l'index. Elle bascule alors sur un parcours séquentiel.

-- Supposons que events ait 50 millions de lignes et un index sur created_at

-- ❌ Parcours complet : YEAR() empêche l'utilisation de l'index
EXPLAIN ANALYZE
SELECT COUNT(*) FROM events WHERE YEAR(created_at) = 2024;

-- Sortie PostgreSQL (simplifiée) :
-- Seq Scan on events  (cost=0.00..4289432.00 rows=5000000 ...)
-- Durée d'exécution : 38 421 ms  ← 38 secondes !

-- ✅ Condition de plage : l'index peut être utilisé
EXPLAIN ANALYZE
SELECT COUNT(*) FROM events
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

-- Sortie PostgreSQL :
-- Index Scan using events_created_at_idx on events (cost=0.57..124832.00 rows=4987234 ...)
-- Durée d'exécution : 312 ms  ← 0,3 seconde
Modèles de fonctions courants et leurs corrections
Motif lentRemplacement rapide
WHERE YEAR(col) = 2024WHERE col >= '2024-01-01' AND col < '2025-01-01'
WHERE DATE(col) = '2024-06-08'WHERE col >= '2024-06-08' AND col < '2024-06-09'
WHERE MONTH(col) = 6WHERE col >= '2024-06-01' AND col < '2024-07-01'
WHERE UPPER(email) = 'ALICE@...'Stocker les emails en minuscules, ou utiliser citext / index insensible à la casse
WHERE TRIM(name) = 'Alice'Nettoyer à l'insertion, pas à la requête
WHERE CAST(id AS TEXT) = '42'WHERE id = 42 (type correct)
WHERE LENGTH(description) > 500Stocker la longueur dans une colonne calculée avec son propre index

Si vous avez vraiment besoin d'interroger fréquemment par le résultat d'une fonction, PostgreSQL prend en charge les index d'expression — un index construit sur la sortie de la fonction plutôt que sur la valeur brute de la colonne :

-- Créer un index sur le résultat de la fonction
CREATE INDEX ON users (LOWER(email));

-- Cette requête utilise maintenant l'index
SELECT id FROM users WHERE LOWER(email) = 'alice@example.com';

-- PostgreSQL a aussi les colonnes générées (depuis la v12)
ALTER TABLE events
  ADD COLUMN event_year SMALLINT GENERATED ALWAYS AS (EXTRACT(YEAR FROM created_at)) STORED;
CREATE INDEX ON events(event_year);

-- Maintenant, c'est soutenu par un index
SELECT COUNT(*) FROM events WHERE event_year = 2024;

Anti-patterns 4 et 5 : UPDATE et DELETE sans WHERE

4-5UPDATE / DELETE sans WHERE
Critique — perte de données

Ces deux-là sont regroupés car le problème et les corrections sont identiques. Un UPDATE users SET actif = false sans clause WHERE touche chaque ligne. Sur une table de 5 millions d'utilisateurs, cela s'exécute silencieusement et se termine en quelques secondes — vous ne le découvrez que lorsque les utilisateurs commencent à appeler le support parce qu'ils ont été déconnectés.

Correction 1 — Toujours utiliser des transactions avec vérification du nombre de lignes
-- PostgreSQL : le modèle de mise à jour sécurisée
BEGIN;

-- Exécuter la mise à jour
UPDATE users SET active = false WHERE email LIKE '%@domaine-obsolete.com';

-- Vérifier combien de lignes ont été affectées AVANT de valider
-- Si le nombre semble anormal, ROLLBACK
SELECT COUNT(*) FROM users WHERE email LIKE '%@domaine-obsolete.com';
-- Ou utiliser : GET DIAGNOSTICS row_count = ROW_COUNT; en PL/pgSQL

-- Ne valider que si le compte est correct
COMMIT;
-- Si quelque chose ne va pas : ROLLBACK;
Correction 2 — Utiliser RETURNING pour voir ce qui a été modifié
-- La clause RETURNING de PostgreSQL vous permet de voir les lignes affectées avant de valider
BEGIN;

-- Supprimer et voir ce que vous êtes sur le point de perdre
DELETE FROM sessions
WHERE expires_at < NOW() - INTERVAL '7 days'
RETURNING id, user_id, created_at;

-- Examinez la sortie. Si elle est correcte :
COMMIT;
-- Sinon :
ROLLBACK;
Correction 3 — Mode sécurisé de MySQL et limites de lignes
-- MySQL : activer les mises à jour sécurisées (bloque UPDATE/DELETE sans WHERE sur une clé)
SET SQL_SAFE_UPDATES = 1;

-- Maintenant, ceci est rejeté :
UPDATE users SET active = false;  -- Erreur : pas de clause WHERE

-- Et ajouter une LIMIT comme garde-fou lors de mises à jour en masse
UPDATE users SET last_notified_at = NOW()
WHERE notification_pending = true
LIMIT 1000;  -- Empêche les mises à jour accidentelles de toute la table
Correction 4 — Suppression logique au lieu de DELETE
-- Ajouter une colonne deleted_at à toutes les tables nécessitant une suppression
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ;

-- "Supprimer" un utilisateur
UPDATE users SET deleted_at = NOW() WHERE id = 42;

-- Interroger les utilisateurs actifs
SELECT * FROM users WHERE deleted_at IS NULL;

-- Avantage : les suppressions massives accidentelles peuvent être récupérées
-- en remettant simplement deleted_at à NULL
UPDATE users SET deleted_at = NULL WHERE id = 42;

Anti-pattern 6 : Jointures cartésiennes

6Jointure cartésienne — l'explosion combinatoire accidentelle
Élevée — performance

Un produit cartésien signifie que chaque ligne de la table A est associée à chaque ligne de la table B. Sur deux tables de 1 000 lignes chacune, le résultat fait 1 000 000 de lignes. Sur deux tables de 100 000 lignes, c'est 10 milliards de lignes. Cela fera planter la plupart des serveurs de base de données ou provoquera des erreurs de mémoire avant de renvoyer des résultats.

-- ❌ Jointure cartésienne accidentelle — syntaxe avec virgule sans condition WHERE
SELECT o.id, u.name, o.total
FROM orders o, users u;
-- Si orders a 50 000 lignes et users 10 000 lignes :
-- Résultat : 500 000 000 lignes
-- Temps d'exécution : ne se terminera jamais sur un serveur normal

-- ✅ JOIN explicite avec une condition
SELECT o.id, u.name, o.total
FROM orders o
INNER JOIN users u ON u.id = o.user_id;
-- Résultat : 50 000 lignes (une par commande)

-- Détecter une jointure cartésienne dans la sortie d'EXPLAIN :
-- PostgreSQL : "Nested Loop" sans condition de jointure affichée
-- MySQL : "Using join buffer (flat, BNL join)" avec toutes les lignes
-- Les lignes estimées seront le produit des deux tables

Les jointures cartésiennes sont parfois intentionnelles — par exemple, pour générer une grille de tous les produits × tous les entrepôts. Dans ce cas, utilisez le mot-clé explicite CROSS JOIN pour clarifier l'intention :

-- Produit cartésien intentionnel — utilisez CROSS JOIN explicitement
SELECT p.id AS product_id, w.id AS warehouse_id
FROM products p
CROSS JOIN warehouses w;
-- Intention claire : il s'agit d'un produit croisé complet

Anti-pattern 7 : Comparer avec = NULL

7WHERE colonne = NULL — toujours faux
Critique — résultats faux

C'est le bug de logique SQL le plus courant pour les développeurs venant d'autres langages. Dans la plupart des langages de programmation, x == null signifie « x est null ». En SQL, colonne = NULL s'évalue à INCONNU — et aucune ligne ne satisfait une condition qui s'évalue à INCONNU. La requête s'exécute avec succès et ne renvoie aucune ligne, même si la colonne contient de nombreuses valeurs NULL.

-- Supposons que orders ait des lignes où shipping_date est NULL (pas encore expédié)
INSERT INTO orders (id, customer_id, shipping_date) VALUES
  (1, 10, '2025-06-01'),
  (2, 11, NULL),          -- Pas encore expédié
  (3, 12, NULL),          -- Pas encore expédié
  (4, 13, '2025-06-05');

-- ❌ Renvoie 0 ligne — NULL = NULL est INCONNU, pas VRAI
SELECT id FROM orders WHERE shipping_date = NULL;

-- ❌ Renvoie également 0 ligne
SELECT id FROM orders WHERE shipping_date != NULL;

-- ✅ Correct
SELECT id FROM orders WHERE shipping_date IS NULL;
-- Renvoie : lignes 2, 3

-- ✅ Correct
SELECT id FROM orders WHERE shipping_date IS NOT NULL;
-- Renvoie : lignes 1, 4

-- ❌ Souvent vu aussi dans des comparaisons sans COALESCE
SELECT * FROM orders WHERE COALESCE(shipping_date, '1970-01-01') = '1970-01-01';
-- Cela fonctionne mais c'est maladroit — préférez IS NULL

Anti-pattern 8 : Le problème des requêtes N+1

8Requêtes N+1 — le piège des ORM
Moyenne — performance à l'échelle

Le problème N+1 est presque invisible en développement, quand votre base de données a 50 lignes. Il surgit en production avec 50 000 lignes, quand un seul endpoint API déclenche soudainement 50 001 requêtes par requête au lieu d'une seule.

Le motif : vous interrogez N utilisateurs, puis pour chaque utilisateur, vous chargez paresseusement ses commandes. Avec le chargement paresseux (par défaut de l'ORM), cela déclenche une requête séparée par utilisateur. N utilisateurs = N+1 requêtes au total.

❌ Motif N+1 (501 requêtes pour 500 utilisateurs)
-- Requête 1 : obtenir tous les utilisateurs
SELECT * FROM users LIMIT 500;

-- Requêtes 2 à 501 : une par utilisateur
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
-- ... 497 requêtes supplémentaires
✅ Motif JOIN (2 requêtes au total)
-- 1 requête : utilisateurs + commandes
SELECT u.id, u.name,
       o.id as order_id, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
ORDER BY u.id
LIMIT 500;
Correction en SQL brut
-- Récupérer les utilisateurs et leur nombre de commandes en une seule requête
SELECT
  u.id,
  u.name,
  u.email,
  COUNT(o.id)   AS order_count,
  COALESCE(SUM(o.total), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.active = true
GROUP BY u.id, u.name, u.email
ORDER BY total_spent DESC
LIMIT 50;
Correction dans SQLAlchemy (Python)
# ❌ N+1 : le chargement paresseux déclenche une requête par utilisateur
users = session.query(User).filter(User.active == True).limit(50).all()
for user in users:
    print(user.orders)  # ← Déclenche une requête ICI pour chaque utilisateur

# ✅ Chargement immédiat : jointure en une seule requête
from sqlalchemy.orm import joinedload

users = (
    session.query(User)
    .options(joinedload(User.orders))  # Joint les commandes dans la même requête
    .filter(User.active == True)
    .limit(50)
    .all()
)
for user in users:
    print(user.orders)  # ← Déjà chargé, pas de requête supplémentaire
Correction dans TypeORM (Node.js)
// ❌ N+1 : les relations ne sont pas chargées dans la requête principale
const users = await User.find({ where: { active: true }, take: 50 });
for (const user of users) {
    const orders = await user.orders; // ← Requête par utilisateur !
}

// ✅ Chargement immédiat avec relations
const users = await User.find({
    where: { active: true },
    relations: ['orders'],  // Chargé avec un JOIN ou une deuxième requête (lot)
    take: 50
});

Anti-pattern 9 : Les différences entre dialectes qui cassent lors d'une migration

Migrer de MySQL vers PostgreSQL (ou vice-versa) est l'une des sources les plus courantes de bugs SQL subtils. Les requêtes semblent valides dans les deux dialectes mais renvoient des résultats différents — parfois un nombre de lignes différent, parfois un ordre différent, parfois une gestion différente de NULL.

LIMIT avec OFFSET : syntaxe opposée entre MySQL et le SQL standard

-- MySQL : LIMIT offset, count (décalage d'abord, puis nombre)
SELECT * FROM users ORDER BY id LIMIT 20, 10;
-- Saute 20 lignes, renvoie les lignes 21-30

-- PostgreSQL / SQLite / SQL standard : LIMIT count OFFSET offset
SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 20;
-- Même résultat : lignes 21-30

-- Un bug de migration courant : les développeurs portent la syntaxe MySQL vers PostgreSQL
SELECT * FROM users ORDER BY id LIMIT 20, 10;
-- PostgreSQL : erreur de syntaxe
-- SQLite : analyse mais traite comme LIMIT 20 (ignore le deuxième paramètre dans certaines versions !)

Différences de gestion de NULL

-- Le tri des NULL diffère selon la base et la directive NULLS FIRST/LAST
-- PostgreSQL : les NULL sont triés EN DERNIER par défaut en ASC, EN PREMIER en DESC
-- MySQL : les NULL sont triés EN PREMIER en ASC
-- SQL Server : les NULL sont triés EN PREMIER

-- Pour un comportement cohérent entre bases, soyez toujours explicite :
SELECT * FROM users ORDER BY subscription_date ASC NULLS LAST;
-- Fonctionne dans PostgreSQL. MySQL ne supporte pas la syntaxe NULLS FIRST/LAST (utilisez une astuce ISNULL)

Sensibilité à la casse des chaînes

-- MySQL avec collation utf8_general_ci : insensible à la casse par défaut
SELECT id FROM users WHERE email = 'ALICE@EXAMPLE.COM';
-- Renvoie les lignes où email = 'alice@example.com' ← peut vous surprendre

-- PostgreSQL : toujours sensible à la casse
SELECT id FROM users WHERE email = 'ALICE@EXAMPLE.COM';
-- Renvoie 0 ligne si stocké en 'alice@example.com'

-- Sûr pour les deux : normalisez à l'insertion, interrogez en minuscules
SELECT id FROM users WHERE email = LOWER('ALICE@EXAMPLE.COM');
-- Ou mieux : imposez les minuscules au niveau applicatif

Rigueur de GROUP BY

-- MySQL (avec ONLY_FULL_GROUP_BY désactivé, ce qui était le défaut avant la 5.7) :
-- Autorise la sélection de colonnes non agrégées qui ne sont pas dans le GROUP BY
SELECT user_id, name, COUNT(*)  -- name n'est pas dans le GROUP BY
FROM orders GROUP BY user_id;   -- MySQL (ancien défaut) : autorisé, valeur arbitraire pour name

-- PostgreSQL (et MySQL 5.7+ avec ONLY_FULL_GROUP_BY) :
-- Erreur : la colonne "name" doit apparaître dans GROUP BY ou être utilisée dans une fonction d'agrégat
-- Correction : ajoutez name au GROUP BY ou utilisez un agrégat
SELECT user_id, MAX(name) AS name, COUNT(*)
FROM orders GROUP BY user_id;

Comment utiliser EXPLAIN ANALYZE pour tous les trouver

Chaque anti-pattern de ce guide laisse une empreinte dans le plan d'exécution de la requête. Une fois que vous savez quoi chercher, EXPLAIN ANALYZE devient votre outil de débogage le plus puissant. Exécutez-le sur toute requête lente avant d'ajouter un index ou de réécrire la requête.

-- PostgreSQL : plan d'exécution complet avec temps réel
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.id, u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.active = true
GROUP BY u.id, u.name
ORDER BY order_count DESC
LIMIT 50;

Foire aux questions

Pourquoi NOT IN avec une sous-requête renvoie-t-il zéro ligne ?

SQL utilise une logique à trois valeurs : VRAI, FAUX et INCONNU. Toute comparaison impliquant NULL s'évalue à INCONNU. NOT IN exige que chaque comparaison soit VRAIE — un seul NULL dans la sous-requête propage l'INCONNU, et aucune ligne ne satisfait une condition qui s'évalue à INCONNU. Le résultat est zéro ligne, silencieusement. Utilisez NOT EXISTS, qui gère NULL correctement : WHERE NOT EXISTS (SELECT 1 FROM t WHERE t.col = outer.col). Ou utilisez une anti-jointure LEFT JOIN : LEFT JOIN t ON t.col = outer.col WHERE t.col IS NULL.

Pourquoi SELECT * est considéré comme une mauvaise pratique ?

Trois raisons : (1) il empêche les index-only scans — si un index contient toutes les colonnes dont vous avez besoin, la base peut répondre depuis l'index sans lire le tas, mais SELECT * force une lecture du tas à chaque fois ; (2) il casse le code applicatif lorsque des colonnes sont ajoutées ou supprimées — une nouvelle colonne ajoutée à une table apparaît soudainement dans chaque réponse d'API ; (3) il gaspille la bande passante réseau entre la base de données et le serveur d'application. Listez toujours les colonnes dont votre requête a réellement besoin. SELECT * est acceptable dans les requêtes de vue de détail et les scripts d'administration rapides, mais jamais dans les requêtes de listing ou de recherche en production.

Qu'est-ce que le problème de requête N+1 ?

Le problème N+1 survient lorsque vous récupérez N enregistrements, puis exécutez une requête supplémentaire par enregistrement pour charger les données liées — soit un total de N+1 requêtes. Un exemple courant : récupérer 100 utilisateurs (1 requête), puis charger les commandes de chaque utilisateur séparément (100 requêtes) = 101 requêtes au total au lieu d'une ou deux. C'est presque invisible en développement avec de petits jeux de données, mais devient catastrophique en production. Corrigez-le avec le chargement immédiat dans votre ORM (joinedload dans SQLAlchemy, relations dans TypeORM) ou en écrivant une requête JOIN manuellement.

Comment me protéger contre un UPDATE ou DELETE accidentel sans WHERE ?

Trois couches de protection : (1) utilisez toujours des transactions — enveloppez le UPDATE/DELETE dans BEGIN/COMMIT et vérifiez le nombre de lignes avant de valider ; (2) utilisez RETURNING (PostgreSQL) pour voir ce qui a réellement été modifié avant de valider ; (3) activez le mode SQL_SAFE_UPDATES de MySQL qui bloque les UPDATE/DELETE sans WHERE sur une clé indexée. Comme pratique d'équipe, n'exécutez jamais de scripts UPDATE/DELETE non testés directement en production — testez d'abord sur une base de données de staging avec une copie des données de production.

Quelle est la différence entre NULL = NULL et NULL IS NULL ?

NULL = NULL s'évalue à INCONNU en SQL — pas VRAI. C'est une décision de conception de la norme SQL. L'opérateur = suit la logique à trois valeurs, et toute comparaison impliquant NULL est INCONNUE. IS NULL est un prédicat spécial qui s'évalue à VRAI lorsque l'opérande est NULL, et FAUX sinon. Utilisez toujours IS NULL et IS NOT NULL pour vérifier les valeurs NULL. N'utilisez jamais = NULL, != NULL, ou <> NULL — ils ne correspondront jamais à aucune ligne.

Pourquoi une fonction dans le WHERE empêche-t-elle l'utilisation d'un index ?

Un index B-tree stocke les valeurs brutes des colonnes dans un ordre trié. Lorsque vous appliquez une fonction à la colonne dans une clause WHERE (comme YEAR(created_at) ou LOWER(email)), la base de données ne peut pas utiliser l'index car elle devrait appliquer la fonction à chaque valeur indexée pour trouver les correspondances. Elle bascule sur un parcours complet de table. Corrigez en réécrivant la condition pour comparer la valeur brute de la colonne : au lieu de WHERE YEAR(created_at) = 2024, utilisez WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'. Pour les fonctions fréquemment utilisées, PostgreSQL supporte les index d'expression : CREATE INDEX ON users (LOWER(email)).

Comment EXPLAIN ANALYZE aide-t-il à identifier les anti-patterns ?

EXPLAIN ANALYZE exécute la requête et montre le plan d'exécution réel avec des temps réels. Signaux clés : un "Seq Scan" (parcours séquentiel) sur une grande table signifie qu'aucun index n'a été utilisé — cherchez un index manquant ou une fonction sur la colonne dans la clause WHERE. Un nombre très élevé de "Rows Removed by Filter" signifie que la plupart du travail est gaspillé. Une différence entre les lignes estimées et réelles indique des statistiques obsolètes — exécutez ANALYZE sur la table. Un "Hash Join" produisant de nombreuses lignes suggère une jointure cartésienne ou une condition de jointure manquante.
