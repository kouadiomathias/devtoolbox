Migrer de SERIAL/AUTO_INCREMENT vers UUID sans interruption

Le plan semblait sans risque sur le papier : ajouter une colonne public_id nullable, la remplir avec UPDATE ... WHERE public_id IS NULL, puis exécuter ALTER TABLE ... SET NOT NULL. Le backfill s'est terminé. Le SET NOT NULL a échoué — une poignée de lignes, insérées par l'application en cours d'exécution dans les secondes entre la fin de la requête de backfill et le début de l'étape suivante de migration, n'avaient aucun public_id. La logique de backfill était correcte ; la colonne n'avait simplement pas encore de défaut, donc chaque insertion du code applicatif — pas encore modifié — créait un nouveau trou. La correction a pris une instruction supplémentaire, placée au bon endroit, avant même que le backfill ne s'exécute.

C'est le détail que la plupart des guides « ajoutez une colonne UUID » passent sous silence, et c'est la différence entre une migration qui fonctionne en staging et une qui échoue sous des écritures concurrentes réelles. Ce guide couvre la séquence complète — un déploiement de colonne sans race condition, un backfill par lots, une manière sans verrou d'imposer NOT NULL sur Postgres 12+, du code spécifique à Django, Rails et Laravel, et un plan de rollback testé — plus la règle d'or que presque toutes les versions de cette migration respectent : ne touchez jamais à vos clés étrangères.

Pourquoi les équipes migrent hors de SERIAL

SERIAL/BIGSERIAL (ou AUTO_INCREMENT en MySQL) sont rapides et compacts, mais ils fuient de l'information dès qu'ils sont exposés dans une URL ou une réponse d'API : un attaquant peut estimer votre rythme de croissance, et une simple boucle incrémentale énumère chaque ressource que vous avez. Une colonne UUID publique corrige cela sans toucher à la clé primaire interne ni à la performance de vos jointures — c'est exactement pourquoi la migration ci-dessous ne remplace jamais la clé primaire elle-même, elle ne fait que s'y ajouter.

Ajouter la colonne sans bloquer les écritures

Cette séquence cible PostgreSQL 12+. Chaque étape est choisie spécifiquement pour éviter les deux modes de défaillance qui rendent cette migration risquée : une réécriture complète de la table, et un verrou tenu longtemps.

Étape 1 — ajouter la colonne, puis définir le défaut séparément

Ajouter une colonne sans défaut ne touche que les métadonnées et est quasi instantané, quelle que soit la taille de la table. Ajouter un défaut volatile comme gen_random_uuid() dans la même instruction ne l'est pas — Postgres doit écrire une valeur distincte dans chaque ligne existante immédiatement, ce qui implique une réécriture complète de la table sous un verrou exclusif. Séparer les deux évite complètement cela, car définir un défaut sur une colonne déjà existante n'affecte que les insertions futures :

-- Étape 1a : instantané, ne touche que les métadonnées
ALTER TABLE users ADD COLUMN public_id UUID;

-- Étape 1b : également rapide — affecte uniquement les lignes insérées à partir de maintenant,
-- ferme la race condition pour toute insertion concurrente avant que le backfill ne démarre
ALTER TABLE users ALTER COLUMN public_id SET DEFAULT gen_random_uuid();

Étape 2 — remplir les lignes existantes par lots

Un seul UPDATE sur toute la table fonctionne pour de petites tables, mais sur une grande, il tient des verrous de ligne longtemps et génère un pic de WAL et de tuples morts pour autovacuum. Un traitement par lots sur la plage de clé primaire garde chaque transaction courte :

DO $$
DECLARE
  batch_size INT := 5000;
  rows_updated INT;
BEGIN
  LOOP
    UPDATE users
    SET public_id = gen_random_uuid()
    WHERE id IN (
      SELECT id FROM users WHERE public_id IS NULL LIMIT batch_size
    );
    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    EXIT WHEN rows_updated = 0;
    COMMIT;
  END LOOP;
END $$;

Étape 3 — imposer NOT NULL sans verrou tenu longtemps

Un simple ALTER COLUMN ... SET NOT NULL force Postgres à scanner toute la table pour confirmer qu'aucune valeur NULL ne subsiste, en tenant un verrou ACCESS EXCLUSIVE pendant tout le scan. Depuis Postgres 12, vous pouvez valider la contrainte séparément d'abord, ce qui rend l'étape finale rapide :

-- Instantané : appliqué immédiatement aux nouvelles lignes, ne scanne pas les existantes
ALTER TABLE users ADD CONSTRAINT public_id_not_null
  CHECK (public_id IS NOT NULL) NOT VALID;

-- Scanne la table, mais ne prend qu'un verrou qui autorise lectures/écritures concurrentes
ALTER TABLE users VALIDATE CONSTRAINT public_id_not_null;

-- Rapide : Postgres peut faire confiance à la contrainte déjà validée au lieu de rescaner
ALTER TABLE users ALTER COLUMN public_id SET NOT NULL;
ALTER TABLE users DROP CONSTRAINT public_id_not_null;

Étape 4 — construire l'index unique en CONCURRENTLY

CREATE UNIQUE INDEX CONCURRENTLY idx_users_public_id ON users(public_id);

CONCURRENTLY construit l'index en arrière-plan sans bloquer les lectures ou écritures. Prévoyez quelques minutes sur une table de plusieurs millions de lignes plutôt que de le traiter comme instantané — mesurez sur une copie de staging de vos vraies données plutôt que de supposer une durée fixe.

01Backfiller avant que la colonne n'ait un défaut
Élevée

Si vous backfillez avant de définir un défaut, chaque ligne que l'application insère entre la requête de backfill et l'étape NOT NULL n'a pas de public_id — exactement l'incident par lequel cet article commence.

Correction
-- L'ordre compte : défaut AVANT backfill, toujours
ALTER TABLE users ADD COLUMN public_id UUID;
ALTER TABLE users ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
-- c'est seulement maintenant qu'on démarre le backfill des lignes NULL existantes

Déployer public_id dans votre API

Une fois la colonne, le backfill, la contrainte et l'index en place, le déploiement vers votre API est une dépréciation en trois étapes bien définies, indépendante du travail de schéma ci-dessus.

Exposer public_id à côté de id

Retournez public_id dans les réponses d'API pendant que id est encore présent en interne. Un exemple Django REST Framework qui correspond à ce schéma hybride :

# serializers.py
class ArticleSerializer(serializers.ModelSerializer):
    id = serializers.UUIDField(source='public_id', read_only=True)

    class Meta:
        model = Article
        fields = ['id', 'title', 'content']
        # 'id' dans la réponse d'API = public_id dans la base de données ;
        # l'id BIGINT interne n'est jamais exposé

Déprécier l'ancien id

Ajoutez un en-tête de réponse Deprecation: true, ou un avertissement documenté, pour tout chemin client qui utilise encore l'ancien id numérique. Fixez une fenêtre — 30 jours est un défaut raisonnable — et surveillez les logs d'accès pour les derniers appels utilisant l'ancien format avant de passer à la suite.

Retirer id des réponses (jamais de la base)

Une fois que les logs montrent plus aucun trafic sur l'ancien identifiant, retirez-le des réponses d'API. La colonne sous-jacente et ses clés étrangères restent exactement telles quelles — cette étape ne change que ce que l'API retourne, pas le schéma.

Spécificités MySQL

MySQL n'a pas d'équivalent à CREATE INDEX CONCURRENTLY. Pour une table activement écrite, un simple ALTER TABLE peut encore bloquer ou sérieusement ralentir les écritures selon la version et le moteur de stockage — utilisez pt-online-schema-change (Percona Toolkit) ou gh-ost (l'outil de migration de schéma en ligne de GitHub) plutôt qu'un ALTER direct sur quoi que ce soit d'autre qu'une petite table ou une fenêtre de maintenance explicite.

-- Approche directe : acceptable pour de petites tables ou une fenêtre de maintenance
ALTER TABLE users ADD COLUMN public_id VARCHAR(36);
UPDATE users SET public_id = UUID();
ALTER TABLE users MODIFY public_id VARCHAR(36) NOT NULL;
ALTER TABLE users ADD UNIQUE INDEX idx_users_public_id (public_id);

-- Grande table activement écrite : utilisez un outil de changement de schéma en ligne
-- pt-online-schema-change alter="ADD COLUMN public_id VARCHAR(36)" D=mydb,t=users
-- ou gh-ost alter="ADD COLUMN public_id VARCHAR(36)" database=mydb table=users

Pour un stockage compact, utilisez BINARY(16) avec UUID_TO_BIN()/BIN_TO_UUID() (MySQL 8.0+) plutôt qu'une chaîne de 36 caractères — le flag de swap maintient les valeurs à peu près triées par insertion, ce qui compte pour la localité d'index :

ALTER TABLE users ADD COLUMN public_id BINARY(16);
UPDATE users SET public_id = UUID_TO_BIN(UUID(), 1);  -- swap_flag=1 : ordonné, favorable à l'index

SELECT BIN_TO_UUID(public_id, 1) as public_id FROM users LIMIT 5;

Django, Rails et Laravel

Django

# models.py — schéma hybride recommandé
import uuid
from django.db import models

class Article(models.Model):
    id = models.AutoField(primary_key=True)  # interne, FK rapides
    public_id = models.UUIDField(default=uuid.uuid4, unique=True, editable=False)
    title = models.CharField(max_length=200)
    content = models.TextField()
# views.py — rechercher par public_id, jamais par id
class ArticleViewSet(viewsets.ModelViewSet):
    queryset = Article.objects.all()
    lookup_field = 'public_id'

Rails

02disable_ddl_transaction! manquant
Élevée

Rails encapsule chaque migration dans une transaction par défaut. PostgreSQL refuse d'exécuter CREATE INDEX CONCURRENTLY à l'intérieur et lève PG::ActiveSqlTransaction: CREATE INDEX CONCURRENTLY cannot run inside a transaction block — un échec au premier lancement très courant pour exactement cette migration.

Correction — et découper le backfill dans sa propre migration
# db/migrate/20260608000001_add_public_id_to_articles.rb
class AddPublicIdToArticles < ActiveRecord::Migration[7.1]
  def change
    add_column :articles, :public_id, :uuid
    change_column_default :articles, :public_id, -> { 'gen_random_uuid()' }
    # backfill des lignes existantes dans une tâche rake séparée ou une autre migration,
    # par lots comme dans l'exemple SQL brut ci-dessus — pas un
    # UPDATE géant à l'intérieur de cette migration
  end
end

# db/migrate/20260608000002_add_public_id_index_to_articles.rb
class AddPublicIdIndexToArticles < ActiveRecord::Migration[7.1]
  disable_ddl_transaction!  # requis pour algorithm: :concurrently

  def change
    change_column_null :articles, :public_id, false
    add_index :articles, :public_id, unique: true, algorithm: :concurrently
  end
end
# app/models/article.rb
class Article < ApplicationRecord
  # public_id a déjà un défaut au niveau base de données — pas de before_create nécessaire
end

# config/routes.rb
resources :articles, param: :public_id

La gem strong_migrations attrape exactement cette classe d'erreur (création d'index non sûre, disable_ddl_transaction! manquant) au moment de la migration — à ajouter à tout projet Rails qui fait des changements de schéma sur une table vivante.

Laravel

// database/migrations/xxxx_add_public_id_to_users.php
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->uuid('public_id')->nullable()->after('id');
    });

    DB::statement('UPDATE users SET public_id = UUID()');

    Schema::table('users', function (Blueprint $table) {
        $table->uuid('public_id')->nullable(false)->change();
        $table->unique('public_id');
    });
}
// app/Models/User.php
use Illuminate\Support\Str;

class User extends Model
{
    protected static function boot(): void
    {
        parent::boot();
        static::creating(function ($model) {
            $model->public_id ??= Str::uuid();
        });
    }

    public function getRouteKeyName(): string
    {
        return 'public_id';
    }
}
Sur une grande table MySQL activement écrite, cette migration Schema::table directe a les mêmes considérations de verrouillage que celles de la section Spécificités MySQL ci-dessus — préférez pt-online-schema-change ou gh-ost plutôt que de l'exécuter directement contre la production.

Monitoring, validation et rollback

Suivre la progression

-- Progression du backfill
SELECT
  COUNT(*) FILTER (WHERE public_id IS NOT NULL) as migrated,
  COUNT(*) FILTER (WHERE public_id IS NULL) as remaining,
  ROUND(100.0 * COUNT(*) FILTER (WHERE public_id IS NOT NULL) / COUNT(*), 1) as pct_done
FROM users;

-- Progression de la construction d'index (PostgreSQL)
SELECT phase, blocks_done, blocks_total,
       ROUND(100.0 * blocks_done / NULLIF(blocks_total, 0), 1) as pct
FROM pg_stat_progress_create_index
WHERE relid = 'users'::regclass;

Vérifications de validation

03Tester l'utilisation de l'index avec une valeur qui ne peut pas matcher
Moyenne

gen_random_uuid() génère une nouvelle valeur aléatoire à chaque appel — la chercher ne teste rien de significatif sur vos données, puisqu'elle ne correspond (très probablement) à aucune ligne.

Ne teste pas un vrai lookup
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE public_id = gen_random_uuid();
-- cherche une valeur qui (presque certainement) n'est pas dans la table
Correction — utilisez une valeur qui existe réellement
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users
WHERE public_id = (SELECT public_id FROM users ORDER BY id LIMIT 1);
-- doit afficher "Index Scan" avec idx_users_public_id, pas "Seq Scan"
-- Vérification d'unicité — les deux comptes doivent correspondre
SELECT COUNT(*), COUNT(DISTINCT public_id) FROM users;

-- Aucun NULL restant — doit retourner 0
SELECT COUNT(*) FROM users WHERE public_id IS NULL;

Pour la latence de lookup ponctuel, mesurez sur une copie de staging de vos vraies données plutôt que de vous fier à une cible fixe en millisecondes — le matériel, l'état du cache et la taille de table font tous bouger ce chiffre. Un lookup d'égalité indexé sur une table correctement dimensionnée devrait être assez rapide pour ne pas apparaître dans un graphique de latence p99 ; s'il apparaît, c'est un signal pour enquêter, pas un nombre autour duquel concevoir à l'avance.

Rollback

-- Rapide : suppression de l'index sans bloquer
DROP INDEX CONCURRENTLY idx_users_public_id;

-- Rapide : la suppression d'une colonne ne touche que les métadonnées dans PostgreSQL
ALTER TABLE users DROP COLUMN public_id;

-- Aucun impact sur les données existantes : id et toutes les clés étrangères sont intactes.
-- Repointez l'API vers l'ancienne version AVANT de rollback le schéma,
-- pas l'inverse.

La règle d'or : ne jamais migrer les clés étrangères vers UUID

C'est le point à retenir après tout le reste de cet article : une clé étrangère BIGINT fait 8 octets et reste rapide à joindre. La convertir en UUID double la taille de chaque index qui la contient, sans aucun bénéfice — public_id existe pour le monde extérieur ; id reste la colonne vertébrale interne du schéma.

Questions fréquentes

Puis-je supprimer mon ancien id auto-incrémenté après la migration ?
Conservez-le en interne — chaque clé étrangère en dépend. Cessez de l'exposer dans l'API, mais ne supprimez jamais la colonne.
Pourquoi ajouter un DEFAULT plutôt que simplement backfiller avec UPDATE ?
Sans défaut, toute ligne insérée entre le backfill et l'étape NOT NULL n'a pas de public_id et fait échouer cette étape. Définir le défaut en premier — une instruction rapide et non bloquante — ferme la faille avant même que le backfill ne démarre.
Ajouter une colonne avec DEFAULT gen_random_uuid() verrouille-t-il la table ?
Oui, si le défaut est défini dans la même instruction ADD COLUMN — un défaut volatile force une réécriture immédiate de chaque ligne. Ajoutez d'abord la colonne sans défaut, puis définissez le défaut séparément ; cette étape n'affecte que les insertions futures et reste rapide quelle que soit la taille de la table.
Pourquoi ma migration Rails échoue avec « CREATE INDEX CONCURRENTLY cannot run inside a transaction block » ?
Rails encapsule les migrations dans une transaction par défaut, et PostgreSQL refuse d'exécuter CONCURRENTLY à l'intérieur. Ajoutez disable_ddl_transaction! à la classe de migration.
Dois-je aussi migrer les clés étrangères vers UUID ?
Non — c'est le moyen le plus rapide de dégrader les performances de jointure sur tout votre schéma. Gardez les clés étrangères en BIGINT et réservez l'UUID à l'identification externe.
