Anti-patterns SQL détectés par cet outil

SELECT * le tueur silencieux de performance

Sélectionner toutes les colonnes avec SELECT * a trois conséquences réelles. Cela empêche les scans d'index seuls — la base de données doit lire la ligne complète même si votre clause WHERE pourrait être satisfaite par un index seul. Cela casse le code applicatif lorsque des colonnes sont ajoutées ou supprimées. Et cela gaspille la bande passante réseau en transférant des données que vous n'utilisez jamais.

NOT IN avec une sous-requête

C'est l'un des motifs SQL les plus dangereux. Si la sous-requête renvoie une valeur NULL, NOT IN ne renvoie aucune ligne — chaque ligne est silencieusement filtrée. Cela provoque des bugs de production quasiment impossibles à déboguer sans connaître ce comportement. Utilisez NOT EXISTS ou LEFT JOIN ... WHERE IS NULL à la place.

- Dangereux : ne renvoie rien si la sous-requête contient un NULL
SELECT id FROM commandes WHERE user_id NOT IN (SELECT id FROM utilisateurs);

  Sûr : NOT EXISTS gère correctement NULL
SELECT id FROM commandes o WHERE NOT EXISTS (
  SELECT 1 FROM utilisateurs u WHERE u.id = o.user_id
);

  Également sûr : motif anti-jointure LEFT JOIN
SELECT o.id FROM commandes o
LEFT JOIN utilisateurs u ON u.id = o.user_id
WHERE u.id IS NULL;

Fonctions sur des colonnes indexées dans les clauses WHERE

Appliquer une fonction à une colonne indexée dans une clause WHERE empêche la base de données d'utiliser cet index. La fonction doit être évaluée pour chaque ligne, ce qui entraîne un parcours complet de la table.

-- ❌ L'index sur date_creation ne peut pas être utilisé
WHERE YEAR(date_creation) = 2024

-- ✅ L'index peut être utilisé avec une condition de plage
WHERE date_creation >= '2024-01-01' AND date_creation < '2025-01-01'

Jointure cartésienne (condition JOIN manquante)

Un FROM table1, table2 sans condition de jointure produit un produit cartésien — chaque ligne de table1 associée à chaque ligne de table2. Sur des tables de 1 000 lignes chacune, cela fait 1 000 000 de lignes. C'est presque toujours une erreur.

WHERE manquant sur UPDATE ou DELETE

Un UPDATE utilisateurs SET actif = false sans clause WHERE met à jour chaque ligne de la table. C'est l'une des causes les plus fréquentes de corruption de données en production. Cet outil signale toute instruction UPDATE ou DELETE sans clause WHERE comme un problème Critique.

Différences entre dialectes référence rapide

 AUTO_INCREMENT (MySQL) vs SERIAL / IDENTITY (PostgreSQL)
 MySQL :
CREATE TABLE users (id INT AUTO_INCREMENT PRIMARY KEY);
 PostgreSQL :
CREATE TABLE users (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY);
 ou plus court :
CREATE TABLE users (id BIGSERIAL PRIMARY KEY);

 LIMIT avec OFFSET
 MySQL : LIMIT offset, count
SELECT * FROM users LIMIT 20, 10;
 PostgreSQL / SQLite / SQL Standard :
SELECT * FROM users LIMIT 10 OFFSET 20;

 Comparaison avec gestion de NULL
 MySQL : IFNULL(val, defaut)
SELECT IFNULL(nom, 'Inconnu') FROM users;
 PostgreSQL / SQL Standard : COALESCE
SELECT COALESCE(nom, 'Inconnu') FROM users;

 Agrégation de chaînes
 MySQL : GROUP_CONCAT
SELECT GROUP_CONCAT(nom ORDER BY nom SEPARATOR ', ') FROM users;
 PostgreSQL : STRING_AGG
SELECT STRING_AGG(nom, ', ' ORDER BY nom) FROM users;

Foire aux questions

Pourquoi SELECT * est une mauvaise pratique ?

SELECT * récupère toutes les colonnes y compris celles inutiles, empêchant les scans d'index seuls, cassant le code applicatif lors de l'ajout ou de la suppression de colonnes, et gaspillant de la bande passante réseau. Listez toujours uniquement les colonnes dont vous avez réellement besoin.

Pourquoi NOT IN avec une sous-requête est dangereux ?

Si la sous-requête renvoie une valeur NULL, NOT IN ne renvoie aucune ligne — filtrant silencieusement tout. Les comparaisons avec NULL utilisant != ou NOT IN renvoient UNKNOWN, et aucune ligne ne satisfait UNKNOWN. Utilisez NOT EXISTS ou un motif anti-jointure LEFT JOIN à la place.

Mes requêtes SQL sont-elles envoyées à un serveur ?

Non. Tout le formatage, l'analyse, l'explication et la conversion se font entièrement dans votre navigateur via JavaScript. Vos requêtes SQL ne quittent jamais votre machine. C'est particulièrement important pour le SQL contenant des noms de tables ou de colonnes qui révèlent votre schéma de base de données.

Que change réellement le convertisseur de dialecte ?

Le convertisseur gère les différences courantes : AUTO_INCREMENT vs SERIAL/IDENTITY, la syntaxe LIMIT, les fonctions de gestion de NULL (IFNULL vs COALESCE), l'agrégation de chaînes (GROUP_CONCAT vs STRING_AGG), les guillemets d'identifiants (backticks vs doubles guillemets) et les alias de types. Il ne réécrit pas les procédures stockées complexes ni les fonctionnalités spécifiques à un dialecte sans équivalent direct.

Qu'est-ce que EXPLAIN ANALYZE ?

EXPLAIN ANALYZE (PostgreSQL) ou EXPLAIN (MySQL) affiche le plan d'exécution de la requête — comment la base de données prévoit d'exécuter votre requête : quels index elle utilise, quelle stratégie de jointure elle choisit, combien de lignes elle estime qu'elle va parcourir. C'est le premier outil à utiliser pour diagnostiquer des requêtes lentes.
