PostgreSQL UUID : gen_random_uuid(), uuidv7() et l'erreur que tout le monde répète

Une table orders avec id uuid PRIMARY KEY DEFAULT gen_random_uuid() a tourné sans problème pendant des millions de lignes. Puis les temps d'insertion ont commencé à grimper et pg_stat_user_indexes affichait un index primaire deux fois plus gros que prévu. Contrairement à MySQL/InnoDB, PostgreSQL ne trie pas physiquement les lignes du heap par clé primaire — le vrai coupable est l'index B-tree lui-même : chaque UUID v4 totalement aléatoire atterrissait sur une page d'index aléatoire au lieu de la dernière page. Résultat : des pages d'index constamment fragmentées, plus d'écritures aléatoires, plus de trafic WAL. Ce n'est pas une mauvaise configuration — c'est le comportement attendu d'une clé primaire UUID v4 à grande échelle.

Depuis PostgreSQL 18 (sorti en septembre 2025), il existe une réponse native à ce problème précis : uuidv7(), un identifiant globalement unique qui s'insère aussi dans l'ordre. Cette page génère les deux versions et montre le SQL correspondant.

Bon point pour PostgreSQL : gen_random_uuid() s'appuie sur un générateur cryptographiquement fort, et ce depuis longtemps — contrairement au UUID() v1 de MySQL, un UUID v4 PostgreSQL ne fuit ni une adresse MAC ni un horodatage exact, et reste raisonnablement sûr à exposer comme identifiant public.

Erreurs courantes avec UUID dans PostgreSQL

01UUID v4 aléatoire comme clé primaire
Élevée

Chaque valeur produite par gen_random_uuid() est uniformément répartie sur 128 bits. Utilisée comme clé primaire, chaque insertion tombe à un endroit aléatoire de l'index B-tree, provoquant des divisions de page constantes.

À éviter (à grande échelle)
sql
CREATE TABLE orders ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), -- aléatoire, fragmente l'index à fort volume amount NUMERIC NOT NULL );
Correction (PostgreSQL 18+)
sql
CREATE TABLE orders ( id uuid PRIMARY KEY DEFAULT uuidv7(), -- ordonné dans le temps, insertions séquentielles amount NUMERIC NOT NULL, created_at timestamptz NOT NULL DEFAULT now() );
02UUID stocké en TEXT au lieu du type natif
Moyenne

Le type uuid de PostgreSQL occupe un volume fixe de 16 octets et se compare directement en binaire. TEXT/VARCHAR(36) ajoute l'en-tête varlena et une comparaison caractère par caractère sensible à la casse — plus volumineux à stocker et à indexer, pour chaque index qui référence la colonne.

Correction
sql
-- toujours le type natif, jamais text/varchar pour un UUID id uuid PRIMARY KEY DEFAULT gen_random_uuid() -- cast si nécessaire (valide le format, erreur sinon) SELECT '12fbc73a-9e9d-44b1-9e6d-1d3e7c8a0f31'::uuid;
03Installer uuid-ossp par réflexe
Faible

Beaucoup de tutoriels en ligne commencent encore par CREATE EXTENSION "uuid-ossp" puis uuid_generate_v4(). Depuis PostgreSQL 13, gen_random_uuid() est disponible nativement (via pgcrypto, déjà inclus) — l'extension externe n'est utile que si vous avez spécifiquement besoin des variantes v1, v3 ou v5.

Correction
sql
-- inutile depuis PG13 pour un simple UUID aléatoire : -- CREATE EXTENSION IF NOT EXISTS "uuid-ossp"; -- uuid_generate_v4() -- suffit, sans extension à installer : SELECT gen_random_uuid();
04Besoin du v7 avant PostgreSQL 18
Moyenne

uuidv7() n'existe qu'à partir de PostgreSQL 18 (septembre 2025). Sur une version antérieure, générez le v7 côté application (toutes les bibliothèques UUID récentes le supportent) ou utilisez une fonction PL/pgSQL de repli.

Fonction de repli (PG 13–17)
sql
CREATE OR REPLACE FUNCTION uuidv7_compat() RETURNS uuid AS $$ DECLARE unix_ts_ms bytea; result uuid; BEGIN unix_ts_ms := substring(int8send(floor(extract(epoch FROM clock_timestamp()) * 1000)::bigint) FROM 3 FOR 6); result := encode( set_bit( set_bit( overlay(uuid_send(gen_random_uuid()) PLACING unix_ts_ms FROM 1 FOR 6), 52, 1 ), 53, 1 ), 'hex' )::uuid; RETURN result; END; $$ LANGUAGE plpgsql VOLATILE; -- utilisation : CREATE TABLE ... id uuid PRIMARY KEY DEFAULT uuidv7_compat()
05Confondre « ordonné » et « sécurisé »
Moyenne

Un UUID v7 encode un horodatage en clair dans ses premiers bits — pratique pour l'indexation, mais il révèle approximativement quand la ligne a été créée. Pour un jeton qui doit rester secret (reset de mot de passe, clé d'API), ne réutilisez jamais l'identifiant de ligne : générez un v4 dédié, entièrement imprévisible.

Correction
sql
CREATE TABLE reset_tokens ( id uuid PRIMARY KEY DEFAULT uuidv7(), -- ordre d'insertion, pas secret token uuid NOT NULL DEFAULT gen_random_uuid(), -- v4 : C'EST le secret envoyé par email user_id uuid NOT NULL REFERENCES users(id) );

Questions fréquentes

Quelle version d'UUID produit gen_random_uuid() ?
La version 4, entièrement aléatoire. Depuis PostgreSQL 18, l'alias uuidv4() a été ajouté pour la cohérence avec uuidv7() — les deux noms produisent le même résultat.
Une clé primaire UUID est-elle plus lente qu'un BIGSERIAL ?
Avec un UUID v4 aléatoire, oui — la fragmentation de l'index B-tree pénalise les performances d'insertion à grande échelle. Avec uuidv7(), les performances d'écriture approchent celles d'un BIGSERIAL, tout en gardant l'avantage d'une génération distribuée sans coordination.
Puis-je utiliser gen_random_uuid() ou uuidv7() comme valeur par défaut ?
Oui, les deux sont des fonctions stables utilisables directement dans une clause DEFAULT — DEFAULT gen_random_uuid() ou, sur PostgreSQL 18+, DEFAULT uuidv7().
Ai-je encore besoin de l'extension uuid-ossp ?
Uniquement si vous avez spécifiquement besoin des versions 1, 3 ou 5. Pour l'usage standard (v4 aléatoire ou, depuis PG18, v7 ordonné), les fonctions natives suffisent et n'exigent aucune extension.
uuidv7() est-il disponible chez mon hébergeur PostgreSQL managé ?
Cela dépend de la version de PostgreSQL que propose votre fournisseur (RDS, Cloud SQL, Supabase, etc.). Vérifiez avec SELECT version(); — si c'est PostgreSQL 18 ou plus récent, uuidv7() est disponible nativement ; sinon, utilisez la fonction de repli PL/pgSQL ci-dessus ou générez du v7 côté application.
Mes données sont-elles envoyées à un serveur ?
Non. Toute la génération d'UUID se fait dans votre navigateur, en JavaScript. Rien de ce qui est affiché ici n'est transmis à un serveur.
