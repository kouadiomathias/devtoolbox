Migrating from SERIAL/AUTO_INCREMENT to UUID Without Downtime

The plan looked safe on paper: add a nullable public_id column, backfill it with UPDATE ... WHERE public_id IS NULL, then run ALTER TABLE ... SET NOT NULL. The backfill finished. The SET NOT NULL failed — a handful of rows, inserted by the running application in the seconds between the backfill query finishing and the next migration step starting, had no public_id at all. Nothing was wrong with the backfill logic; the column simply didn't have a default yet, so every insert from the still-unmodified application code produced a fresh gap. The fix took one extra statement, added in the right place, before the backfill even ran.

That's the detail most "add a UUID column" guides skip, and it's the difference between a migration that works in staging and one that fails under real concurrent writes. This guide covers the full sequence — a race-free column rollout, batched backfill, a lock-free way to enforce NOT NULL on Postgres 12+, framework-specific code for Django, Rails and Laravel, and a tested rollback plan — plus the golden rule almost every version of this migration gets right: never touch your foreign keys.

Why teams migrate away from SERIAL

SERIAL/BIGSERIAL (or AUTO_INCREMENT in MySQL) are fast and compact, but they leak information the moment they're exposed in a URL or API response: an attacker can estimate your growth rate, and a simple incrementing loop enumerates every resource you have. A public UUID column fixes that without touching the internal primary key or your join performance — which is exactly why the migration below never replaces the primary key itself, only adds alongside it.

Adding the column without locking writes

This sequence targets PostgreSQL 12+. Each step is chosen specifically to avoid the two failure modes that make this migration risky: a full table rewrite, and a long-held lock.

Step 1 — add the column, then set the default separately

Adding a column with no default is metadata-only and effectively instant, regardless of table size. Adding a volatile default like gen_random_uuid() in the same statement is not — Postgres has to write a distinct value into every existing row immediately, which means a full table rewrite under an exclusive lock. Splitting the two avoids that entirely, because setting a default on an already-existing column only affects future inserts:

-- Step 1a: instant, metadata-only
ALTER TABLE users ADD COLUMN public_id UUID;

-- Step 1b: also fast — affects only rows inserted from now on,
-- closing the race for any concurrent insert before backfill starts
ALTER TABLE users ALTER COLUMN public_id SET DEFAULT gen_random_uuid();

Step 2 backfill existing rows in batches

A single UPDATE over the whole table works for small tables, but on a large one it holds row locks for a long time and generates a burst of WAL and dead tuples for autovacuum to clean up. Batching by primary key range keeps each transaction short:

DO $$
DECLARE
  batch_size INT := 5000;
  rows_updated INT;
BEGIN
  LOOP
    UPDATE users
    SET public_id = gen_random_uuid()
    WHERE id IN (
      SELECT id FROM users WHERE public_id IS NULL LIMIT batch_size
    );
    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    EXIT WHEN rows_updated = 0;
    COMMIT;
  END LOOP;
END $$;

Step 3 enforce NOT NULL without a long-held lock

A plain ALTER COLUMN ... SET NOT NULL forces Postgres to scan the whole table to confirm no NULL values remain, while holding an ACCESS EXCLUSIVE lock for the entire scan. Since Postgres 12, you can validate the constraint separately first, so the final step is fast:

-- Instant: enforced for new rows immediately, doesn't scan existing ones
ALTER TABLE users ADD CONSTRAINT public_id_not_null
  CHECK (public_id IS NOT NULL) NOT VALID;

-- Scans the table, but only takes a lock that allows concurrent reads/writes
ALTER TABLE users VALIDATE CONSTRAINT public_id_not_null;

-- Fast: Postgres can trust the already-validated constraint instead of re-scanning
ALTER TABLE users ALTER COLUMN public_id SET NOT NULL;
ALTER TABLE users DROP CONSTRAINT public_id_not_null;

Step 4 — build the unique index CONCURRENTLY

CREATE UNIQUE INDEX CONCURRENTLY idx_users_public_id ON users(public_id);

CONCURRENTLY builds the index in the background without blocking reads or writes. Budget a few minutes on a multi-million-row table rather than treating it as instantaneous — measure on a staging copy of your real data rather than assuming a fixed duration.

01Backfilling before the column has a default
High

If you backfill before setting a default, every row the application inserts between the backfill query and the NOT NULL step has no public_id — exactly the incident this article opens with.

Fix
-- Order matters: default BEFORE backfill, always
ALTER TABLE users ADD COLUMN public_id UUID;
ALTER TABLE users ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
 only now start backfilling existing NULL rows

Rolling out public_id in your API

Once the column, backfill, constraint, and index are in place, the rollout to your API is a straightforward three-step deprecation, independent of the schema work above.

Expose public_id alongside id

Return public_id in API responses while id is still present internally. A Django REST Framework example that fits this hybrid pattern:

# serializers.py
class ArticleSerializer(serializers.ModelSerializer):
    id = serializers.UUIDField(source='public_id', read_only=True)

    class Meta:
        model = Article
        fields = ['id', 'title', 'content']
        # 'id' in the API response = public_id in the database;
        # the internal BIGINT id is never exposed

Deprecate the old id

Add a Deprecation: true response header, or a documented warning, for any client path still keying on the old numeric id. Give a fixed window — 30 days is a reasonable default — and monitor access logs for the last calls using the old format before moving on.

Remove id from responses (never from the database)

Once logs show no remaining traffic on the old identifier, drop it from API responses. The underlying column and its foreign keys stay exactly as they are — this step only changes what the API returns, not the schema.

MySQL specifics

MySQL has no equivalent of CREATE INDEX CONCURRENTLY. For an actively-written table, a plain ALTER TABLE can still block or seriously slow down writes depending on version and storage engine — use pt-online-schema-change (Percona Toolkit) or gh-ost (GitHub's online schema migration tool) instead of a direct ALTER on anything but a small table or an explicit maintenance window.

 Direct approach: fine for small tables or a maintenance window
ALTER TABLE users ADD COLUMN public_id VARCHAR(36);
UPDATE users SET public_id = UUID();
ALTER TABLE users MODIFY public_id VARCHAR(36) NOT NULL;
ALTER TABLE users ADD UNIQUE INDEX idx_users_public_id (public_id);

 Large, actively-written table: use an online schema change tool instead
 pt-online-schema-change alter "ADD COLUMN public_id VARCHAR(36)" D=mydb,t=users
 or gh-ost alter="ADD COLUMN public_id VARCHAR(36)" database=mydb table=users

For compact storage, use BINARY(16) with UUID_TO_BIN()/BIN_TO_UUID() (MySQL 8.0+) instead of a 36-character string — the swap flag keeps values roughly insertion-ordered, which matters for index locality:

ALTER TABLE users ADD COLUMN public_id BINARY(16);
UPDATE users SET public_id = UUID_TO_BIN(UUID(), 1);   swap_flag=1: ordered, index-friendly

SELECT BIN_TO_UUID(public_id, 1) as public_id FROM users LIMIT 5;

Django, Rails, and Laravel

Django

# models.py recommended hybrid pattern
import uuid
from django.db import models

class Article(models.Model):
    id = models.AutoField(primary_key=True)  # internal, fast FKs
    public_id = models.UUIDField(default=uuid.uuid4, unique=True, editable=False)
    title = models.CharField(max_length=200)
    content = models.TextField()
# views.py look up by public_id, never id
class ArticleViewSet(viewsets.ModelViewSet):
    queryset = Article.objects.all()
    lookup_field = 'public_id'

Rails

02Missing disable_ddl_transaction!
High

Rails wraps every migration in a transaction by default. PostgreSQL refuses to run CREATE INDEX CONCURRENTLY inside one and raises PG::ActiveSqlTransaction: CREATE INDEX CONCURRENTLY cannot run inside a transaction block — a very common first-run failure for exactly this migration.

Fix — and split the backfill into its own migration
# db/migrate/20260608000001_add_public_id_to_articles.rb
class AddPublicIdToArticles < ActiveRecord::Migration[7.1]
  def change
    add_column :articles, :public_id, :uuid
    change_column_default :articles, :public_id, -> { 'gen_random_uuid()' }
    # backfill existing rows in a separate rake task or migration,
    # batched the same way as the raw-SQL example above — not one
    # giant UPDATE inside this migration
  end
end

# db/migrate/20260608000002_add_public_id_index_to_articles.rb
class AddPublicIdIndexToArticles < ActiveRecord::Migration[7.1]
  disable_ddl_transaction!  # required for algorithm: :concurrently

  def change
    change_column_null :articles, :public_id, false
    add_index :articles, :public_id, unique: true, algorithm: :concurrently
  end
end
# app/models/article.rb
class Article < ApplicationRecord
  # public_id already has a DB-level default no before_create needed
end

# config/routes.rb
resources :articles, param: :public_id

The strong_migrations gem catches this exact class of mistake (unsafe index creation, missing disable_ddl_transaction!) at migration time — worth adding to any Rails project doing schema changes on a live table.

Laravel

// database/migrations/xxxx_add_public_id_to_users.php
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->uuid('public_id')->nullable()->after('id');
    });

    DB::statement('UPDATE users SET public_id = UUID()');

    Schema::table('users', function (Blueprint $table) {
        $table->uuid('public_id')->nullable(false)->change();
        $table->unique('public_id');
    });
}
// app/Models/User.php
use Illuminate\Support\Str;

class User extends Model
{
    protected static function boot(): void
    {
        parent::boot();
        static::creating(function ($model) {
            $model->public_id ??= Str::uuid();
        });
    }

    public function getRouteKeyName(): string
    {
        return 'public_id';
    }
}
On a large, actively-written MySQL table, this direct Schema::table migration has the same locking considerations covered in the MySQL specifics section above — reach for pt-online-schema-change or gh-ost rather than running it directly against production.

Monitoring, validation, and rollback

Monitoring progress

-- Backfill progress
SELECT
  COUNT(*) FILTER (WHERE public_id IS NOT NULL) as migrated,
  COUNT(*) FILTER (WHERE public_id IS NULL) as remaining,
  ROUND(100.0 * COUNT(*) FILTER (WHERE public_id IS NOT NULL) / COUNT(*), 1) as pct_done
FROM users;

-- Index build progress (PostgreSQL)
SELECT phase, blocks_done, blocks_total,
       ROUND(100.0 * blocks_done / NULLIF(blocks_total, 0), 1) as pct
FROM pg_stat_progress_create_index
WHERE relid = 'users'::regclass;

Validation checks

03Testing index usage with a value that can't match
Medium

gen_random_uuid() generates a brand-new random value every time it's called — searching for it tests nothing meaningful about your data, since it (overwhelmingly likely) matches no row at all.

Doesn't test a real lookup
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE public_id = gen_random_uuid();
-- searches for a value that (almost certainly) isn't in the table
Fix use a value that actually exists
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users
WHERE public_id = (SELECT public_id FROM users ORDER BY id LIMIT 1);
 should show "Index Scan" using idx_users_public_id, not "Seq Scan"
 Uniqueness sanity check both counts must match
SELECT COUNT(*), COUNT(DISTINCT public_id) FROM users;

 No NULLs left must return 0
SELECT COUNT(*) FROM users WHERE public_id IS NULL;

For point-lookup latency, measure on a staging copy of your real data rather than trusting a fixed millisecond target — hardware, cache state, and table size all move that number. An indexed equality lookup on a properly-sized table should be fast enough not to show up in a p99 latency graph; if it does, that's a signal to investigate, not a number to design around in advance.

Rollback

 Fast: drop the index without blocking
DROP INDEX CONCURRENTLY idx_users_public_id;

 Fast: dropping a column is metadata-only in PostgreSQL
ALTER TABLE users DROP COLUMN public_id;

 No impact on existing data id and all foreign keys are untouched.
 Route the API back to the old version before rolling back the schema,
 not the other way around.

The golden rule: never migrate foreign keys to UUID

This is the point worth remembering after everything else in this article: a BIGINT foreign key is 8 bytes and fast to join on. Converting it to UUID doubles the size of every index that includes it, for no benefit — public_id exists for the outside world; id stays the internal backbone of the schema.

Frequently asked questions

Can I remove my old auto-increment id after the migration?
Keep it internally — every foreign key depends on it. Stop exposing it in the API, but never drop the column.
Why add a DEFAULT instead of just backfilling with UPDATE?
Without a default, any row inserted between the backfill and the NOT NULL step has no public_id and fails that step. Setting the default first — itself a fast, non-blocking statement — closes the gap before backfill even starts.
Does adding a column with DEFAULT gen_random_uuid() lock the table?
Yes, if the default is set in the same ADD COLUMN statement — a volatile default forces an immediate rewrite of every row. Add the column with no default first, then set the default separately; that step only affects future inserts and is fast regardless of table size.
Why does my Rails migration fail with "CREATE INDEX CONCURRENTLY cannot run inside a transaction block"?
Rails wraps migrations in a transaction by default, and PostgreSQL won't run CONCURRENTLY inside one. Add disable_ddl_transaction! to the migration class.
Should I migrate foreign keys to UUID too?
No — that's the fastest way to hurt join performance across your schema. Keep foreign keys as BIGINT and reserve UUID for external identification.
