The DELETE that emptied a production table

It was a Friday afternoon. A developer on a team I know was running a cleanup script to remove test accounts from the production database. The query was supposed to be:

DELETE FROM users WHERE email LIKE '%@test.example.com';

What was actually executed:

DELETE FROM users;

The WHERE clause had been accidentally removed while editing the script. The query ran in 0.8 seconds. All 340,000 users were gone. The application was instantly down. The rollback took three hours from a backup that was six hours old, which meant six hours of production signups were permanently lost.

This is the most dramatic SQL anti-pattern, but it's far from the only dangerous one. Some anti-patterns destroy data. Others destroy performance quietly — you don't notice until your database is serving 10 million rows instead of 10,000 and every API call takes 8 seconds instead of 80 milliseconds. A few are subtle logic bugs that produce wrong results while looking entirely correct — the NOT IN with NULL pattern being the worst offender.

This guide covers the 10 patterns that cause the most damage in real production systems, with reproducible examples and the exact fixes.

Anti-pattern 1: NOT IN with a subquery the silent wrong result

1NOT IN with NULL in subquery
Critical wrong results

This is the most dangerous SQL bug because it produces no error. Your query runs, returns results, and everything looks normal — except you're missing rows that should be there, or getting no rows at all when you expect many.

The cause is SQL's three-valued logic. SQL doesn't have just TRUE and FALSE it has TRUE, FALSE, and UNKNOWN. Any comparison with NULL evaluates to UNKNOWN. And here's the critical part: NOT IN filters out rows where the comparison is not TRUE. UNKNOWN is not TRUE. So any row being compared against a NULL value in the subquery is filtered out.

The reproducible bug
-- Setup: users table where one row has a NULL country
CREATE TABLE users (id INT, name VARCHAR(50), country VARCHAR(2));
INSERT INTO users VALUES
  (1, 'Alice', 'FR'),
  (2, 'Bob',   'DE'),
  (3, 'Carol', NULL);   -- ← This NULL is the bomb

-- Blocked countries
CREATE TABLE blocked_countries (country_code VARCHAR(2));
INSERT INTO blocked_countries VALUES ('US'), ('CN');

 Expected: rows 1, 2, 3 (none of them are US or CN)
 Actual:   0 rows (!)
SELECT id, name FROM users
WHERE country NOT IN (SELECT country_code FROM blocked_countries);

 Why? The NOT IN expands to:
 WHERE country != 'US' AND country != 'CN'
 For row 3: NULL != 'US' → UNKNOWN; UNKNOWN AND ... → UNKNOWN
 UNKNOWN is not TRUE → row 3 is filtered out
 But because row 3 is filtered, the query also filters rows 1 and 2
 due to how the optimizer handles NULL in the NOT IN list.
 The exact behavior depends on the database, but the safest rule is:
 never use NOT IN if the subquery can return NULL.
Fix 1 NOT EXISTS (recommended)
-- NOT EXISTS handles NULL correctly
 Returns rows 1, 2, 3 as expected
SELECT id, name FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM blocked_countries b
  WHERE b.country_code = u.country
);
-- NOT EXISTS short-circuits correctly:
-- For row 3 (country = NULL): the subquery WHERE NULL = country_code
-- never matches, so NOT EXISTS is TRUE. Row 3 is included. ✓
Fix 2 LEFT JOIN anti-join pattern
-- Also handles NULL correctly, and often performs better on large tables
SELECT u.id, u.name
FROM users u
LEFT JOIN blocked_countries b ON u.country = b.country_code
WHERE b.country_code IS NULL;
-- Rows where no match was found (including NULL country) are returned ✓
Fix 3 Add WHERE IS NOT NULL (if NULLs should be excluded)
-- If you want to exclude NULL countries explicitly
SELECT id, name FROM users
WHERE country IS NOT NULL
  AND country NOT IN (SELECT country_code FROM blocked_countries
                      WHERE country_code IS NOT NULL);

Anti-pattern 2: SELECT * three costs that compound

2SELECT * the apparently harmless habit
Medium performance + brittleness

Most developers know SELECT * is "bad". Fewer know exactly why, which means they don't know when it actually matters versus when it's acceptable. There are three distinct costs, and each one compounds at scale.

Cost 1 No index-only scans

PostgreSQL (and other databases) can answer a query entirely from an index without touching the actual table rows — an "index-only scan." This is dramatically faster because indexes are smaller and more likely to be cached. SELECT * destroys this: since the index doesn't contain every column, the database must visit the actual heap (table data) for every matching row.

 Table with an index on (user_id)
CREATE TABLE events (
  id         UUID PRIMARY KEY,
  user_id    BIGINT,
  event_type VARCHAR(50),
  payload    JSONB,     Potentially large
  created_at TIMESTAMPTZ
);
CREATE INDEX ON events(user_id);

  Forces a heap fetch for every row  index alone isn't enough
SELECT * FROM events WHERE user_id = 42;

  Index-only scan possible if index covers needed columns
SELECT id, event_type, created_at FROM events WHERE user_id = 42;

 Even better: create a covering index
CREATE INDEX ON events(user_id) INCLUDE (id, event_type, created_at);
  Now the query above never touches the heap

Cost 2 Schema brittleness

Your frontend expects users to have 8 columns. You add a password_reset_token column for a new feature. Every API endpoint that does SELECT * FROM users now exposes that token in its response. This isn't hypothetical — it's a pattern I've seen cause security incidents in production. The "security by accident" that SELECT * provides is the worst kind: you don't know what you're exposing.

Cost 3 Unnecessary bandwidth

If your products table has a description TEXT column averaging 2 KB, and a listing query that returns 200 products does SELECT *, you're transferring 400 KB of description text that the listing page never displays. At 100 requests per second, that's 40 MB/s of unnecessary database-to-app network traffic. Use SELECT id, name, price, thumbnail_url for the listing, and only fetch the full product (including description) when a user views the detail page.

-- ❌ Listing query  all columns including large ones
SELECT * FROM products WHERE category_id = 5 ORDER BY created_at DESC LIMIT 20;

 ✅ Listing query — only what the UI displays
SELECT id, name, price, stock, thumbnail_url, slug
FROM products
WHERE category_id = 5
ORDER BY created_at DESC
LIMIT 20;

 ✅ Detail query  full product when user clicks
SELECT * FROM products WHERE slug = 'widget-pro-xl';
 (SELECT * is fine here  we need everything)
When SELECT * is acceptable: In a detail view that genuinely needs all columns, in quick one-off admin scripts, or when querying a small reference table with a stable schema. The key word is "intentionally" — you know exactly what you're selecting, not leaving it to chance.

Anti-pattern 3: Functions on indexed columns in WHERE

3Function on indexed column the invisible full scan
High performance

This is probably the most common performance anti-pattern I encounter in code review. The query looks clean, the logic is correct, but the database ignores the index and reads every row in the table.

The reason is straightforward: an index on created_at stores raw timestamp values in sorted order. If you apply YEAR(created_at) or DATE(created_at) to the column, the database would need to evaluate the function for every stored value to apply the filter — which defeats the purpose of the index. It falls back to a sequential scan.

-- Assume events has 50 million rows and an index on created_at

 Full scan: YEAR() prevents index usage
EXPLAIN ANALYZE
SELECT COUNT(*) FROM events WHERE YEAR(created_at) = 2024;

 PostgreSQL output (simplified):
 Seq Scan on events  (cost=0.00..4289432.00 rows=5000000 ...)
 Execution Time: 38,421 ms  ← 38 seconds!

 Range condition: index can be used
EXPLAIN ANALYZE
SELECT COUNT(*) FROM events
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

 PostgreSQL output:
 Index Scan using events_created_at_idx on events (cost=0.57..124832.00 rows=4987234 ...)
 Execution Time: 312 ms  ← 0.3 seconds
Common function patterns and their fixes
Slow patternFast replacement
WHERE YEAR(col) = 2024WHERE col >= '2024-01-01' AND col < '2025-01-01'
WHERE DATE(col) = '2024-06-08'WHERE col >= '2024-06-08' AND col < '2024-06-09'
WHERE MONTH(col) = 6WHERE col >= '2024-06-01' AND col < '2024-07-01'
WHERE UPPER(email) = 'ALICE@...'Store emails lowercase, or use citext / case-insensitive index
WHERE TRIM(name) = 'Alice'Sanitize on insert, not on query
WHERE CAST(id AS TEXT) = '42'WHERE id = 42 (correct type)
WHERE LENGTH(description) > 500Store length in a computed column with its own index

If you genuinely need to query by a function result frequently, PostgreSQL supports expression indexes — an index built on the function output rather than the raw column value:

 Create an index on the function result
CREATE INDEX ON users (LOWER(email));

- This query now uses the index
SELECT id FROM users WHERE LOWER(email) = 'alice@example.com';

- PostgreSQL also has generated columns (since v12)
ALTER TABLE events
  ADD COLUMN event_year SMALLINT GENERATED ALWAYS AS (EXTRACT(YEAR FROM created_at)) STORED;
CREATE INDEX ON events(event_year);

- Now this is index-backed
SELECT COUNT(*) FROM events WHERE event_year = 2024;

Anti-pattern 4 & 5: UPDATE and DELETE without WHERE

4-5UPDATE / DELETE without WHERE
Critical data loss

These two are grouped because the problem and the fixes are identical. An UPDATE users SET active = false without a WHERE clause touches every row. On a table with 5 million users, this runs silently and completes in a few seconds — you don't find out until users start calling support because they've been logged out.

Fix 1 Always use transactions with a row count check
-- PostgreSQL: the safe update pattern
BEGIN;

-- Run the update
UPDATE users SET active = false WHERE email LIKE '%@deprecated-domain.com';

-- Check how many rows were affected BEFORE committing
-- If the number looks wrong, ROLLBACK
SELECT COUNT(*) FROM users WHERE email LIKE '%@deprecated-domain.com';
-- Or use: GET DIAGNOSTICS row_count = ROW_COUNT; in PL/pgSQL

-- Only commit if the count looks right
COMMIT;
-- If something's wrong: ROLLBACK;
Fix 2 Use RETURNING to verify what was modified
-- PostgreSQL's RETURNING lets you see the affected rows before committing
BEGIN;

  Delete and see what you're about to lose
DELETE FROM sessions
WHERE expires_at < NOW()  INTERVAL '7 days'
RETURNING id, user_id, created_at;

- Review the output. If it looks correct:
COMMIT;
- If not:
ROLLBACK;
Fix 3 MySQL safe mode and row limits
-- MySQL: enable safe updates (blocks UPDATE/DELETE without WHERE on a key)
SET SQL_SAFE_UPDATES = 1;

-- Now this is rejected:
UPDATE users SET active = false;   Error: no WHERE clause

-- And add a LIMIT as a safeguard when mass-updating
UPDATE users SET last_notified_at = NOW()
WHERE notification_pending = true
LIMIT 1000;   Prevents accidental full-table updates
Fix 4 Soft delete instead of DELETE
-- Add a deleted_at column to all tables that need deletion
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ;

-- "Delete" a user
UPDATE users SET deleted_at = NOW() WHERE id = 42;

-- Query active users
SELECT * FROM users WHERE deleted_at IS NULL;

-- Advantage: accidental mass "deletions" can be recovered
-- by simply setting deleted_at back to NULL
UPDATE users SET deleted_at = NULL WHERE id = 42;

Anti-pattern 6: Cartesian joins

6Cartesian join the accidental combinatorial explosion
High performance

A Cartesian product means every row in table A is matched with every row in table B. On two tables with 1,000 rows each, the result has 1,000,000 rows. On two tables with 100,000 rows each, it's 10 billion rows. This will crash most database servers or cause OOM errors before returning results.

 Accidental Cartesian join  comma syntax without a WHERE condition
SELECT o.id, u.name, o.total
FROM orders o, users u;
 If orders has 50,000 rows and users has 10,000 rows:
 Result: 500,000,000 rows
-- Runtime: will never complete on a normal server

-- ✅ Explicit JOIN with a condition
SELECT o.id, u.name, o.total
FROM orders o
INNER JOIN users u ON u.id = o.user_id;
-- Result: 50,000 rows (one per order)

-- Detecting a Cartesian join in EXPLAIN output:
-- PostgreSQL: "Nested Loop" with no join condition shown
-- MySQL: "Using join buffer (flat, BNL join)" with all rows
-- The estimated rows will be the product of both tables

Cartesian joins are sometimes intentional — for example, generating a grid of all products × all warehouses. In that case, use the explicit CROSS JOIN keyword to make the intent clear:

-- Intentional Cartesian product  use CROSS JOIN explicitly
SELECT p.id AS product_id, w.id AS warehouse_id
FROM products p
CROSS JOIN warehouses w;
-- Clear intent: this is supposed to be a full cross product

Anti-pattern 7: Comparing with = NULL

7WHERE column = NULL always wrong
Critical wrong results

This is the most common SQL logic bug for developers coming from other languages. In most programming languages, x == null means "x is null." In SQL, column = NULL evaluates to UNKNOWN — and no row satisfies a condition that evaluates to UNKNOWN. The query runs successfully and returns zero rows, even if the column contains many NULL values.

 Assume orders has rows where shipping_date is NULL (not yet shipped)
INSERT INTO orders (id, customer_id, shipping_date) VALUES
  (1, 10, '2025-06-01'),
  (2, 11, NULL),          - Not shipped yet
  (3, 12, NULL),          - Not shipped yet
  (4, 13, '2025-06-05');

- ❌ Returns 0 rows  NULL = NULL is UNKNOWN, not TRUE
SELECT id FROM orders WHERE shipping_date = NULL;

- ❌ Also returns 0 rows
SELECT id FROM orders WHERE shipping_date != NULL;

-- ✅ Correct
SELECT id FROM orders WHERE shipping_date IS NULL;
- Returns: rows 2, 3

- ✅ Correct
SELECT id FROM orders WHERE shipping_date IS NOT NULL;
- Returns: rows 1, 4

- ❌ Also often seen in COALESCE-less comparisons
SELECT * FROM orders WHERE COALESCE(shipping_date, '1970-01-01') = '1970-01-01';
- This works but is awkward  prefer IS NULL

Anti-pattern 8: The N+1 query problem

8N+1 queries the ORM trap
Medium — performance at scale

The N+1 problem is almost never visible during development, when your database has 50 rows. It surfaces in production with 50,000 rows, when a single API endpoint suddenly fires 50,001 queries per request instead of 1.

The pattern: you query for N users, then for each user you lazily load their orders. With lazy loading (the ORM's default), this triggers a separate query per user. N users = N+1 queries total.

❌ N+1 pattern (501 queries for 500 users)
-- Query 1: get all users
SELECT * FROM users LIMIT 500;

-- Query 2 through 501: one per user
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
-- ... 497 more queries
✅ JOIN pattern (2 queries total)
-- 1 query: users + orders
SELECT u.id, u.name,
       o.id as order_id, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
ORDER BY u.id
LIMIT 500;
Fix in raw SQL
-- Fetch users and their order counts in one query
SELECT
  u.id,
  u.name,
  u.email,
  COUNT(o.id)   AS order_count,
  COALESCE(SUM(o.total), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.active = true
GROUP BY u.id, u.name, u.email
ORDER BY total_spent DESC
LIMIT 50;
Fix in SQLAlchemy (Python)
# ❌ N+1: lazy loading triggers a query per user
users = session.query(User).filter(User.active == True).limit(50).all()
for user in users:
    print(user.orders)  # ← Triggers a query HERE for each user

# ✅ Eager loading: joins in a single query
from sqlalchemy.orm import joinedload

users = (
    session.query(User)
    .options(joinedload(User.orders))  # Join orders in the same query
    .filter(User.active == True)
    .limit(50)
    .all()
)
for user in users:
    print(user.orders)  # ← Already loaded, no extra query
Fix in TypeORM (Node.js)
// ❌ N+1: relations not loaded in the main query
const users = await User.find({ where: { active: true }, take: 50 });
for (const user of users) {
    const orders = await user.orders; // ← Query per user!
}

// ✅ Eager loading with relations
const users = await User.find({
    where: { active: true },
    relations: ['orders'],  // Loaded with a JOIN or second query (batch)
    take: 50
});

Anti-pattern 9: Dialect differences that break on migration

Migrating from MySQL to PostgreSQL (or vice versa) is one of the most common sources of subtle SQL bugs. The queries look valid in both dialects but return different results — sometimes different row counts, sometimes different ordering, sometimes different NULL handling.

LIMIT with OFFSET: opposite syntax between MySQL and standard SQL

 MySQL: LIMIT offset, count (offset first, then count)
SELECT * FROM users ORDER BY id LIMIT 20, 10;
- Skips 20 rows, returns rows 21-30

- PostgreSQL / SQLite / Standard SQL: LIMIT count OFFSET offset
SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 20;
- Same result: rows 21-30

- A common migration bug: developers port the MySQL syntax to PostgreSQL
SELECT * FROM users ORDER BY id LIMIT 20, 10;
- PostgreSQL: syntax error
- SQLite: parses but treats as LIMIT 20 (ignores the second parameter in some versions!)

NULL handling differences

 NULL sorting differs by database and NULLS FIRST/LAST directive
- PostgreSQL: NULLs sort LAST by default in ASC, FIRST in DESC
- MySQL: NULLs sort FIRST in ASC
- SQL Server: NULLs sort FIRST

- For consistent behavior across databases, always be explicit:
SELECT * FROM users ORDER BY subscription_date ASC NULLS LAST;
- Works in PostgreSQL. MySQL doesn't support NULLS FIRST/LAST syntax (use ISNULL trick)

String comparison case sensitivity

 MySQL with utf8_general_ci collation: case-insensitive by default
SELECT id FROM users WHERE email = 'ALICE@EXAMPLE.COM';
- Returns rows where email = 'alice@example.com' ← might surprise you

- PostgreSQL: always case-sensitive
SELECT id FROM users WHERE email = 'ALICE@EXAMPLE.COM';
- Returns 0 rows if stored as 'alice@example.com'

- Safe for both: normalize on insert, query in lowercase
SELECT id FROM users WHERE email = LOWER('ALICE@EXAMPLE.COM');
- Or better: enforce lowercase at the application layer

GROUP BY strictness

-- MySQL (with ONLY_FULL_GROUP_BY off, which was the pre-5.7 default):
- Allows selecting non-aggregated columns not in GROUP BY
SELECT user_id, name, COUNT(*)   name is not in GROUP BY
FROM orders GROUP BY user_id;    MySQL (old default): allowed, arbitrary name value

- PostgreSQL (and MySQL 5.7+ with ONLY_FULL_GROUP_BY):
- Error: column "name" must appear in GROUP BY or be used in aggregate
- Fix: add name to GROUP BY or use an aggregate
SELECT user_id, MAX(name) AS name, COUNT(*)
FROM orders GROUP BY user_id;

How to use EXPLAIN ANALYZE to find all of these

Every anti-pattern in this guide leaves a fingerprint in the query execution plan. Once you know what to look for, EXPLAIN ANALYZE becomes your most powerful debugging tool. Run it on any slow query before adding an index or rewriting the query.

 PostgreSQL: full execution plan with actual timing
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.id, u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.active = true
GROUP BY u.id, u.name
ORDER BY order_count DESC
LIMIT 50;
Limit (cost=12834.23..12834.35 rows=50) (actual time=342.1..342.2 rows=50) -> Sort (cost=12834.23..12956.89 rows=49064) (actual time=342.1..342.1 rows=50) Sort Key: (count(o.id)) DESC -> HashAggregate (cost=8234.12..9707.88 rows=49064) -> Seq Scan on users u (cost=0.00..4123.00 rows=49064) ← ⚠️ FULL SCAN Filter: (active = true) Rows Removed by Filter: 51000 -> Hash -> Index Scan using orders_user_id_idx on orders o ← ✅ Index used Planning Time: 2.3 ms Execution Time: 342.6 ms ← could be 12ms with an index on users(active)

The Seq Scan on users tells you the active column has no index. Adding one would change this to an Index Scan and drop the execution time significantly.

Frequently asked questions

Why does NOT IN with a subquery return zero rows?

SQL uses three-valued logic: TRUE, FALSE, and UNKNOWN. Any comparison involving NULL evaluates to UNKNOWN. NOT IN requires every comparison to be TRUE — a single NULL in the subquery causes UNKNOWN to propagate, and no row satisfies a condition that evaluates to UNKNOWN. The result is zero rows, silently. Use NOT EXISTS, which handles NULL correctly: WHERE NOT EXISTS (SELECT 1 FROM t WHERE t.col = outer.col). Or use a LEFT JOIN anti-join: LEFT JOIN t ON t.col = outer.col WHERE t.col IS NULL.

Why is SELECT * considered bad practice?

Three reasons: (1) it prevents index-only scans if an index contains all the columns you need, the database can answer from the index without reading the heap, but SELECT * forces a heap read every time; (2) it breaks application code when columns are added or removed — a new column added to a table suddenly appears in every API response; (3) it wastes network bandwidth between the database and application server. Always list the columns your query actually needs. SELECT * is acceptable in detail view queries and quick admin scripts, but never in production listing or search queries.

What is the N+1 query problem?

The N+1 problem occurs when you fetch N records and then execute one additional query per record to load related data — totaling N+1 queries. A common example: fetch 100 users (1 query), then load each user's orders separately (100 queries) = 101 queries total instead of 1 or 2. This is almost invisible in development with small datasets but becomes catastrophic in production. Fix it with eager loading in your ORM (joinedload in SQLAlchemy, relations in TypeORM) or by writing a JOIN query manually.

How do I protect against accidental UPDATE or DELETE without WHERE?

Three layers of protection: (1) always use transactions wrap the UPDATE/DELETE in BEGIN/COMMIT and check the row count before committing; (2) use RETURNING (PostgreSQL) to see what was actually modified before committing; (3) enable MySQL's SQL_SAFE_UPDATES mode which blocks UPDATE/DELETE without a WHERE on an indexed key. As a team practice, never run untested UPDATE/DELETE scripts directly in production — test on a staging database with a copy of production data first.

What is the difference between NULL = NULL and NULL IS NULL?

NULL = NULL evaluates to UNKNOWN in SQL — not TRUE. This is by design in the SQL standard. The = operator follows three-valued logic, and any comparison involving NULL is UNKNOWN. IS NULL is a special predicate that evaluates to TRUE when the operand is NULL and FALSE otherwise. Always use IS NULL and IS NOT NULL to check for NULL values. Never use = NULL, != NULL, or <> NULL — they will never match any row.

Why does a function in WHERE prevent index usage?

A B-tree index stores raw column values in sorted order. When you apply a function to the column in a WHERE clause (like YEAR(created_at) or LOWER(email)), the database cannot use the index because it would need to apply the function to every indexed value to find matches. It falls back to a full table scan. Fix by rewriting the condition to compare the raw column value: instead of WHERE YEAR(created_at) = 2024, use WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'. For frequently-used functions, PostgreSQL supports expression indexes: CREATE INDEX ON users (LOWER(email)).

How does EXPLAIN ANALYZE help identify anti-patterns?

EXPLAIN ANALYZE executes the query and shows the actual execution plan with real timings. Key signals: a "Seq Scan" (sequential scan) on a large table means no index was used — look for a missing index or a function on the column in the WHERE clause. A very high "Rows Removed by Filter" count means most work is being discarded. A mismatch between estimated and actual rows means stale statistics — run ANALYZE on the table. A "Hash Join" producing many rows suggests a Cartesian join or missing join condition.
