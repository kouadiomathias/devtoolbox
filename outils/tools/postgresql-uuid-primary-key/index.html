PostgreSQL UUID: gen_random_uuid(), uuidv7() and the Mistake Everyone Repeats

On this page
  1. The index that kept growing
  2. Decision table
  3. Common UUID pitfalls in PostgreSQL
  4. FAQ
  5. References

A orders table with id uuid PRIMARY KEY DEFAULT gen_random_uuid() ran fine for millions of rows. Then insert times started climbing and pg_stat_user_indexes showed a primary index twice as large as expected. Unlike MySQL/InnoDB, PostgreSQL does not physically sort heap rows by the primary key – the real culprit is the B-tree index itself: every fully random UUID v4 landed on a random index page instead of the last page. The result: constantly fragmenting index pages, more random writes, more WAL traffic. This is not a misconfiguration – it is the expected behavior of a UUID v4 primary key at scale.

Since PostgreSQL 18 (released September 2025), there is a native answer to this exact problem: uuidv7(), a globally unique identifier that also inserts in order. This page generates both versions and shows the matching SQL.

Good for PostgreSQL: gen_random_uuid() relies on a cryptographically strong generator and has for a long time – unlike MySQL's v1 UUID(), a PostgreSQL v4 UUID leaks neither a MAC address nor an exact timestamp, and is reasonably safe to expose as a public identifier.

Common UUID pitfalls in PostgreSQL

01Random UUID v4 as primary key
High

Every value produced by gen_random_uuid() is uniformly distributed across 128 bits. Used as a primary key, each insert falls at a random spot in the B-tree index, causing constant page splits.

Avoid (at scale)
sql
CREATE TABLE orders ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), -- random, fragments the index at high volume amount NUMERIC NOT NULL );
Fix (PostgreSQL 18+)
sql
CREATE TABLE orders ( id uuid PRIMARY KEY DEFAULT uuidv7(), -- time-ordered, sequential inserts amount NUMERIC NOT NULL, created_at timestamptz NOT NULL DEFAULT now() );
02UUID stored as TEXT instead of the native type
Medium

PostgreSQL's uuid type occupies a fixed 16 bytes and compares directly in binary. TEXT/VARCHAR(36) adds the varlena header and a case‑sensitive character‑by‑character comparison – bulkier to store and index, for every index that references the column.

Fix
sql
-- always the native type, never text/varchar for a UUID id uuid PRIMARY KEY DEFAULT gen_random_uuid() -- cast if needed (validates the format, errors otherwise) SELECT '12fbc73a-9e9d-44b1-9e6d-1d3e7c8a0f31'::uuid;
03Installing uuid-ossp by reflex
Low

Many online tutorials still start with CREATE EXTENSION "uuid-ossp" then uuid_generate_v4(). Since PostgreSQL 13, gen_random_uuid() is available natively (via pgcrypto, already included) – the external extension is only useful if you specifically need v1, v3, or v5 variants.

Fix
sql
-- unnecessary since PG13 for a simple random UUID: -- CREATE EXTENSION IF NOT EXISTS "uuid-ossp"; -- uuid_generate_v4() -- enough, with no extension to install: SELECT gen_random_uuid();
04Needing v7 before PostgreSQL 18
Medium

uuidv7() only exists from PostgreSQL 18 (September 2025) onward. On an earlier version, generate v7 on the application side (all recent UUID libraries support it) or use a PL/pgSQL fallback function.

Fallback function (PG 13–17)
sql
CREATE OR REPLACE FUNCTION uuidv7_compat() RETURNS uuid AS $$ DECLARE unix_ts_ms bytea; result uuid; BEGIN unix_ts_ms := substring(int8send(floor(extract(epoch FROM clock_timestamp()) * 1000)::bigint) FROM 3 FOR 6); result := encode( set_bit( set_bit( overlay(uuid_send(gen_random_uuid()) PLACING unix_ts_ms FROM 1 FOR 6), 52, 1 ), 53, 1 ), 'hex' )::uuid; RETURN result; END; $$ LANGUAGE plpgsql VOLATILE; -- usage: CREATE TABLE ... id uuid PRIMARY KEY DEFAULT uuidv7_compat()
05Confusing "ordered" with "secure"
Medium

A UUID v7 encodes a plain timestamp in its first bits – handy for indexing, but it reveals roughly when the row was created. For a token that must stay secret (password reset, API key), never reuse the row identifier: generate a dedicated, fully unpredictable v4.

Fix
sql
CREATE TABLE reset_tokens ( id uuid PRIMARY KEY DEFAULT uuidv7(), -- insertion order, not secret token uuid NOT NULL DEFAULT gen_random_uuid(), -- v4: THIS is the secret sent by email user_id uuid NOT NULL REFERENCES users(id) );

Frequently asked questions

What UUID version does gen_random_uuid() produce?
Version 4, fully random. Since PostgreSQL 18, the alias uuidv4() has been added for consistency with uuidv7() – both names produce the same result.
Is a UUID primary key slower than BIGSERIAL?
With a random UUID v4, yes – B-tree index fragmentation hurts insert performance at scale. With uuidv7(), write performance approaches that of a BIGSERIAL, while keeping the advantage of distributed generation without coordination.
Can I use gen_random_uuid() or uuidv7() as a default value?
Yes, both are stable functions usable directly in a DEFAULT clause – DEFAULT gen_random_uuid() or, on PostgreSQL 18+, DEFAULT uuidv7().
Do I still need the uuid-ossp extension?
Only if you specifically need versions 1, 3, or 5. For standard usage (v4 random or, since PG18, v7 ordered), the native functions are sufficient and require no extension.
Is uuidv7() available on my managed PostgreSQL provider?
It depends on the PostgreSQL version your provider offers (RDS, Cloud SQL, Supabase, etc.). Check with SELECT version(); – if it is PostgreSQL 18 or newer, uuidv7() is available natively; otherwise, use the PL/pgSQL fallback above or generate v7 on the application side.
Is my data sent to a server?
No. All UUID generation happens in your browser, in JavaScript. Nothing shown here is transmitted to a server.
