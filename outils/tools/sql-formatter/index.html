SQL anti-patterns this tool detects

SELECT * the silent performance killer

Selecting all columns with SELECT * has three real costs. It prevents index-only scans — the database must visit the actual row even if your WHERE clause could be satisfied by an index alone. It breaks application code when columns are added or removed. And it wastes network bandwidth transferring data you never use.

NOT IN with a subquery

This is one of the most dangerous SQL patterns. If the subquery returns any NULL value, NOT IN returns zero rows — every single row is silently filtered out. This causes production bugs that are almost impossible to debug without knowing this behavior. Use NOT EXISTS or LEFT JOIN ... WHERE IS NULL instead.

 Dangerous: returns no rows if subquery has any NULL
SELECT id FROM orders WHERE user_id NOT IN (SELECT id FROM users);

 Safe: NOT EXISTS handles NULL correctly
SELECT id FROM orders o WHERE NOT EXISTS (
  SELECT 1 FROM users u WHERE u.id = o.user_id
);

 Also safe: LEFT JOIN anti-join pattern
SELECT o.id FROM orders o
LEFT JOIN users u ON u.id = o.user_id
WHERE u.id IS NULL;

Functions on indexed columns in WHERE clauses

Applying a function to an indexed column in a WHERE clause prevents the database from using that index. The function must be evaluated for every row, resulting in a full table scan.

 Index on created_at cannot be used
WHERE YEAR(created_at) = 2024

 Index can be used with a range condition
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

Cartesian join (missing JOIN condition)

A FROM table1, table2 without a join condition produces a Cartesian product — every row in table1 matched with every row in table2. On tables with 1 000 rows each, that's 1 000 000 rows. This is almost always a mistake.

Missing WHERE on UPDATE or DELETE

An UPDATE users SET active = false without a WHERE clause updates every row in the table. This is one of the most common causes of production data corruption. This tool flags any UPDATE or DELETE statement without a WHERE clause as a Critical finding.

Dialect differences quick reference

-- AUTO_INCREMENT (MySQL) vs SERIAL / IDENTITY (PostgreSQL)
-- MySQL:
CREATE TABLE users (id INT AUTO_INCREMENT PRIMARY KEY);
 PostgreSQL:
CREATE TABLE users (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY);
 or shorter:
CREATE TABLE users (id BIGSERIAL PRIMARY KEY);

 LIMIT with OFFSET
 MySQL: LIMIT offset, count
SELECT * FROM users LIMIT 20, 10;
 PostgreSQL / SQLite / Standard SQL:
SELECT * FROM users LIMIT 10 OFFSET 20;

 NULL-safe comparison
 MySQL: IFNULL(val, default)
SELECT IFNULL(name, 'Unknown') FROM users;
 PostgreSQL / Standard SQL: COALESCE
SELECT COALESCE(name, 'Unknown') FROM users;

 String aggregation
 MySQL: GROUP_CONCAT
SELECT GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') FROM users;
 PostgreSQL: STRING_AGG
SELECT STRING_AGG(name, ', ' ORDER BY name) FROM users;

Frequently Asked Questions

Why is SELECT * a bad practice?

SELECT * retrieves all columns including unused ones. This prevents index-only scans (the database must read the full row even if the index has all needed data), breaks application code when columns are added or removed, and wastes network bandwidth. Always list only the columns you actually need.

Why is NOT IN with a subquery dangerous?

If the subquery returns any NULL value, NOT IN returns zero rows — every single row is filtered out. This is because NULL comparisons with != or NOT IN return UNKNOWN (not TRUE or FALSE), and no row satisfies a condition that evaluates to UNKNOWN. Use NOT EXISTS or a LEFT JOIN anti-join pattern instead.

Is my SQL sent to a server when I use this tool?

No. All formatting, analysis, explanation, and conversion happens entirely in your browser using JavaScript and WebAssembly. Your SQL queries never leave your machine. This is especially important for SQL that contains table names, column names, or data that reveals your database schema.

What does the dialect converter actually change?

The converter handles common differences: AUTO_INCREMENT vs SERIAL/IDENTITY, LIMIT syntax, NULL-handling functions (IFNULL vs COALESCE), string aggregation (GROUP_CONCAT vs STRING_AGG), identifier quoting (backticks vs double quotes), and type aliases. It does not rewrite complex stored procedures or dialect-specific features that have no direct equivalent.

What is EXPLAIN ANALYZE?

EXPLAIN ANALYZE (PostgreSQL) or EXPLAIN (MySQL) shows the query execution plan — how the database actually plans to execute your query: which indexes it uses, what join strategy it chooses, how many rows it estimates it will scan. This is the first tool to reach for when diagnosing slow queries.
