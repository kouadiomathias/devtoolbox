UUID collision probability: the real numbers, not the hand-wavy rules

On this page
  1. The calculator that lied at both extremes
  2. Quick decision table
  3. Common collision-calculation mistakes
  4. FAQ
  5. References

A collision-probability formula built around 1 - Math.exp(x) looks harmless until you test its edges. Hand it a small, realistic number of identifiers and it silently returns exactly 0 instead of a tiny-but-nonzero probability — floating-point catastrophic cancellation wipes out every significant digit. Hand it a huge number, past the point where collisions are essentially certain, and it returns 0 again, for the opposite reason: the exponent underflows and an early guard clause reports "impossible" when the honest answer is "almost certain". Neither failure throws an error. Both just return a confident, wrong number. The fix is one function: -Math.expm1(x) instead of 1 - Math.exp(x), which stays numerically accurate across the whole range.

The other number worth double-checking is how many random bits an identifier actually has. It's often assumed that UUID v7 is "as unique as v4" because both are 128 bits total — but v7 spends 48 of those bits on a timestamp, leaving 74 random bits, not 122. That's not a rounding difference: the 50% collision threshold for a 74-bit identifier is about 17 million times lower than for a 122-bit one.

The birthday-problem formula only applies to identifiers drawn independently and uniformly at random into a fixed space. Timestamp-prefixed IDs, counters, and coordinated schemes require a different (usually much stronger) uniqueness argument.

Common collision-calculation mistakes

011 − exp(x) instead of −expm1(x)
High

For small values of |x|, Math.exp(x) rounds to something extremely close to 1, and subtracting from 1 destroys almost every significant digit of the result — a textbook case of catastrophic cancellation.

Avoid
javascript
const p = 1 - Math.exp(exponent); // rounds to exactly 0 for small |exponent|, and to 0 (wrong) for a huge negative exponent too
Fix
javascript
const p = -Math.expm1(exponent); // accurate near 0, and correctly approaches 1 for a huge negative exponent
02Confusing total bits with random bits
High

Any identifier that embeds a timestamp, a counter, or a fixed prefix has fewer random bits than its total length. Only the random part feeds the birthday-problem math.

Wrong
text
UUID v7 → 128 bits total → treated as 128 bits of entropy // ignores the 48-bit timestamp
Right
text
UUID v7 → 128 bits total − 48-bit timestamp − 4-bit version − 2-bit variant = 74 random bits
03Applying the formula to non-random schemes
Medium

Snowflake IDs and auto-increment counters are unique by construction — a coordinated timestamp/worker/sequence, or a single authoritative counter — not because they sample randomly from a large space. Running birthday-problem math on them produces a number that doesn't mean what it looks like it means.

Fix
text
Auto-increment: 0% collision by construction (single sequence authority) Snowflake: collision-free as long as worker IDs and clocks don't conflict — not a matter of probability

Frequently asked questions

Can two UUID v4 values actually be identical?
Yes, in theory — but you'd have to generate roughly 2.7 × 1018 UUIDs to have a 50% chance of a single collision. Generating one billion UUIDs per second without pause would take about 86 years to reach that number.
Are UUID v4 collisions a real concern in practice?
No. At any realistic scale, other failure modes — application bugs, replication lag, hardware failures — are vastly more likely than a random UUID collision. A unique constraint at the database level is a reasonable safety net, but a pre-insert existence check isn't necessary.
How does UUID v7 really compare to v4 for collisions?
v7 has 74 random bits versus 122 for v4, because 48 bits are dedicated to a millisecond timestamp. The 50% collision threshold drops from about 2.7 × 1018 identifiers to about 1.6 × 1011 — still an enormous number for almost any application, but significantly smaller, and worth knowing if you generate at very high volume within the same millisecond bursts.
Are all 96 bits of a MongoDB ObjectID random?
No. An ObjectID is composed of a 4-byte timestamp, a 5-byte value randomly generated once per process, and a 3-byte counter that increments per document. Only the 5-byte random component (40 bits) varies unpredictably between processes; the counter part is sequential, not random.
Why does the calculator treat Snowflake and auto-increment IDs differently?
Because the birthday problem describes what happens when values are drawn independently at random. Snowflake IDs and auto-increment counters are built to avoid collisions by design (coordination or single sequence), so a collision-probability framing doesn't really apply to them the way it does to UUIDs.
Is my data sent anywhere when I use this calculator?
No. All calculations run locally in your browser in JavaScript. Nothing you enter here is transmitted anywhere.
